# 날짜 중심 탐색 + 파일 단위 재생 현황 — 계획안

> 요청 정리
> ① CH0/CH1 라벨이 영상 OSD 글자와 겹침
> ② 날짜 단위로 끊어서, **캘린더에서 날짜를 클릭**하면 그 날짜만 재생
> ③ 연속 재생하되 **각 영상 파일 단위의 재생 현황**이 보이게
> ④ `⏮⏭` = 이전/다음 **파일**, `◀▶` = **10초** 뒤/앞
> ⑤ 폴더 열 때 전체를 다 읽지 말고 **인덱스만 읽어 날짜·시간대를 정리**한 뒤,
>    선택한 날짜만 로딩
>
> 실측 기준: 이 저장소 환경, 680개 파일(data 660 + event 20) 합성 폴더.
>
> **결정 완료 (구현됨)** — D5 월간 캘린더 · D6 공백 10분 세션 분리 ·
> D7 캘린더만 띄우고 대기 · D8 IndexedDB 캐시.
> 구현하며 추가로 고친 것은 11장에 정리했습니다.

## 1. 지금 무엇이 문제인가 (측정)

660개 구간을 실제로 열어 재본 결과입니다.

| 항목 | 측정값 | 판단 |
|---|---|---|
| 폴더 열기(헤더 프로브 680개) | 2.1초 | 이 환경에선 빠름. 모바일은 더 느릴 것 |
| 전 구간 GPS·센서 스캔(660개) | 2.9초 | 지금은 **무조건 전부** 돈다 |
| JS 힙 | 35MB | 문제 없음 |
| **타임라인 스트립 구간 폭** | **0.15%** | **치명적** |

### 스트립이 못 쓰게 된 이유

전체 범위가 **230시간 45분**(9월 3일~12일)인데 파일 하나는 69초입니다.
비율로 0.0083% → 최소 폭 보정을 걸어도 0.15%, 1200px 화면에서 **1.8px짜리 실**입니다.
보내주신 화면에서 세로 실선들이 그것입니다. 클릭으로 원하는 지점을 고르는 건 불가능합니다.

또 시간 라벨이 `134:15:58 / 231:37:37` 로 나옵니다. **230시간 중 134시간째**라는 숫자는
사람이 쓸 수 있는 정보가 아닙니다. 실제로 알고 싶은 건 "지금 몇 시 영상인가"와
"이 파일에서 어디쯤인가" 두 가지입니다.

> **진단**: 병합 자체는 맞았지만, **전체를 하나의 축에 올린 것**이 틀렸습니다.
> 230시간 중 실제 영상은 12.6시간(5.5%)뿐이고 나머지는 주차·정차 공백입니다.
> 날짜로 끊으면 축이 24시간(실질 1~3시간)으로 줄어 비율이 100배 나아집니다.

## 2. "전체를 다 읽는다"에 대하여 — 사실 확인

짚어주신 부분인데, 현재도 **파일 전체를 읽지는 않습니다.**

| 단계 | 읽는 양 | 680개 합계 |
|---|---|---|
| 헤더 프로브 | 파일당 **512바이트** | 0.35MB |
| 전 구간 GPS·센서 스캔 | 파일당 **약 0.1MB** | **약 66MB** |

58GB 중 66MB이니 0.11%입니다. 다만 **지적하신 방향이 맞습니다** —
GPS 스캔 66MB는 지금 **날짜를 고르기도 전에** 전부 돌고 있고, 이건 낭비입니다.
모바일에서 파일 하나 열 때마다 붙는 오버헤드까지 감안하면 체감이 훨씬 클 겁니다.

**한 가지 양해를 구할 부분**: 캘린더를 그리려면 어느 파일이 어느 날짜인지 알아야 하므로
**헤더 프로브(512B)는 모든 파일에 대해 한 번은 해야 합니다.** 파일명이 순번이라
다른 방법이 없습니다. 대신 이걸 두 가지로 줄입니다.

1. 프로브를 **첫 화면(캘린더)까지만** 하고, GPS 스캔은 **선택한 날짜만**
2. 프로브 결과를 **IndexedDB에 캐시** → 같은 폴더를 다시 열면 즉시 캘린더 (D8)

## 3. 새 구조 — 3단 탐색

```
① 폴더 열기
   └ 헤더 프로브(512B × N)  ~2초
        ↓
② 캘린더                        ← 새로 만듦
   ┌──────────────────────┐
   │  2026년 9월          │
   │  일 월 화 수 목 금 토 │
   │      1  2 [3][4][5] 6 │   ← 녹화 있는 날만 활성
   │   7 [8][9][10][11][12]│      셀에 파일 수·총 길이
   │  13 14 15 ...         │
   └──────────────────────┘
        ↓ 날짜 클릭
③ 그 날짜만 로딩 (GPS 스캔 83개 ≈ 1.6초)
   └ 하루 타임라인 + 연속 재생
```

### ② 캘린더에서 보여줄 것

- 녹화가 있는 날만 활성화, **막대 길이로 그날 녹화량** 표시 (히트맵)
- 셀 안: `83개 · 1:35` (파일 수 · 총 녹화 길이)
- 여러 달에 걸치면 월 이동. 데이터가 있는 첫/마지막 달로 자동 제한
- 폴더(`data`/`event`) 선택은 캘린더 위에 유지

### ③ 날짜를 고른 뒤 화면

```
┌─────────────────┬─────────────────┐
│  전방 CH0  [CH0]│  후방 CH1  [CH1]│  ← 라벨을 우측 상단으로
│                 │                 │
│  09-08 22:25 32km/h  IROAD        │  ← 기기 OSD (하단)
└─────────────────┴─────────────────┘
 [⏮] [↺10] [▶] [10↻] [⏭]   ← 파일 이동 / 10초 / 재생
 ━━━━━━━━━●━━━━━━━━━━━━━━━   ← 현재 파일 안에서의 위치
 0:24 / 1:08  ·  구간 12/83  ·  00000417.jdr

 ▓▓ ▓▓▓▓ ░░░░░░ ▓▓▓▓▓▓▓▓ ░░ ▓▓▓   ← 그날 전체(24h) 타임라인
 08:09          12:00          23:46
 기록 시각 2026-09-08 22:25:17 · 32.0 km/h · 37.242029, 127.170268
```

**핵심 변경**: 메인 슬라이더가 **전체 230시간이 아니라 현재 파일 69초**를 나타냅니다.
"연속 재생하되 현황은 파일 단위로"라는 요청 그대로입니다.
날짜 전체 이동은 아래 타임라인 스트립을 클릭해서 합니다.

## 4. 컨트롤 재정의

| 버튼 | 동작 | 비고 |
|---|---|---|
| `⏮` | **이전 파일** | 재생 3초 이내면 이전 파일로, 아니면 현재 파일 처음으로 (미디어 플레이어 관례). D7에서 결정 |
| `↺10` | **10초 뒤로** | 파일 경계를 넘어가면 이전 파일 끝부분으로 |
| `▶ / ❚❚` | 재생 / 일시정지 | Space |
| `10↻` | **10초 앞으로** | 파일 경계를 넘어가면 다음 파일로 |
| `⏭` | **다음 파일** | |
| 슬라이더 | 현재 파일 안에서 이동 | |
| 스트립 | 그날 아무 시각으로 이동 | 빈 구간은 다음 녹화로 건너뜀 |
| 프레임 단위 | `,` `.` 키 | 버튼에서는 뺌 (자리도 없고 일상 조작이 아님) |

10초는 주요 플레이어들의 사실상 표준입니다. 아이콘도 숫자를 넣은 화살표(`↺10`)로 만들어
"10초"임을 글자로 보이게 합니다.

## 9. 작업 범위

### 1단계 — 날짜 인덱스 + 캘린더
- `core/calendar`: 세그먼트를 날짜별로 묶고 날짜별 통계 산출
- `ui/calendar`: 월간 그리드, 녹화량 히트맵, 월 이동
- 폴더를 열면 캘린더 먼저, 전 구간 GPS 스캔은 제거

### 2단계 — 날짜 한정 타임라인 + 파일 단위 현황
- 선택 날짜만으로 Library 구성
- 메인 슬라이더를 현재 파일 기준으로 전환
- `0:24 / 1:08 · 구간 12/83 · 00000417.jdr` 표시
- 스트립을 하루 범위로

### 3단계 — 컨트롤 재정의
- 이전/다음 파일, ±10초, 경계 넘는 10초 이동
- CH 라벨 위치·가독성

### 4단계 — 캐시 (D8에서 채택 시)
- IndexedDB에 프로브 결과 저장 (키: 파일명+크기+수정시각)
- 재방문 시 즉시 캘린더

## 11. 구현 결과

### 측정 (680개 파일)

| 단계 | 이전 | 지금 |
|---|---|---|
| 폴더 열기 → 첫 화면 | 2.1초 (바로 재생 화면) | 2.1초 (캘린더) |
| **다시 열기** | 2.1초 | **0.6초** (IndexedDB 캐시) |
| 날짜 열기 → 재생 준비 | — | **0.1초** |
| GPS·센서 스캔 | **2.9초** (660개 전부) | **0.4초** (선택 날짜 79개) |
| JS 힙 | 35MB | **12MB** |

### 타임라인 축을 고쳤습니다 (계획에 없던 부분)

날짜로 끊은 뒤에도 **구간 폭이 0.15% 그대로**였습니다.
하루 범위가 15.6시간(오전·오후 운행 사이 13시간 공백)이라 공백이 축을 다 먹기 때문입니다.

그래서 스트립 축을 **빈 구간만 눌러 담는 방식**으로 바꿨습니다.

- 각 구간은 실제 길이에 비례
- 빈 구간은 축의 2%씩, 전부 합쳐 30%를 넘지 않게 압축
- **빈 구간을 없애지는 않습니다** — 빗금으로 계속 보이고 툴팁에 실제 길이가 나옵니다
- 시간 순서도 그대로입니다

D2에서 정한 "벽시계 축 + 빈 구간 표시"의 취지(공백을 숨기지 않음)는 지키면서,
클릭할 수 있게 만든 절충입니다.

| | 구간 폭 | 1200px 화면에서 |
|---|---|---|
| 이전 (벽시계 비율 그대로) | 0.15% | 1.8px |
| 날짜 전체 (79개) | **1.24%** | **14.9px** |
| 운행 하나 (40개) | **2.50%** | **30.0px** |

### 구현 중 발견해 고친 버그

| 버그 | 증상 | 원인 |
|---|---|---|
| **⏭ 연타가 먹히지 않음** | 구간 전환 중 누른 버튼이 조용히 무시됨 | 전환에 수백 ms가 걸리는 동안 들어온 요청을 버렸음 → 마지막 요청을 기억했다가 이어서 처리 |
| **숨긴 화면이 보임** | 캘린더 위에 재생 화면이 겹쳐 보임 | `.app { display: grid }` 가 `[hidden]` 속성을 덮어씀 → `[hidden] { display: none !important }` |
| 모바일 상단바 글자 깨짐 | 버튼 글자가 세로로 쪼개짐 | 좁은 화면용 짧은 라벨 추가 |
| 캘린더 셀이 화면을 다 먹음 | 정사각형 셀 + 막대가 셀 전체를 채움 | 셀 높이 고정, 막대는 하단 34%만 |

- 여러 구간에 걸친 병합 내보내기 (지금은 재생 중인 구간 하나만)
- 70MB × 2채널 고화질을 모바일에서 동시 디코딩할 수 있는지 실기기 확인
- Chrome Android 147 미만에서 폴더 선택 불가 → 감지 후 안내 (파일 열기는 동작)

## 12. 인덱스 파일 (추가 구현)

브라우저 캐시(D8)만으로는 부족하다는 지적을 받아 **인덱스 파일**을 추가했습니다.

### 브라우저 캐시의 한계

| | IndexedDB 캐시 | 인덱스 파일 |
|---|---|---|
| 기기·브라우저 이동 | ❌ | ✅ PC에서 만들어 폰에서 사용 |
| 브라우저 데이터 삭제 | ❌ 사라짐 | ✅ 남음 |
| 단일 HTML 위치 이동 | ❌ origin이 달라져 사라짐 | ✅ 무관 |
| 다른 사람에게 전달 | ❌ | ✅ 폴더와 함께 전달 |
| 사람이 열어볼 수 있음 | ❌ | ✅ JSON |

> 참고: Chrome 계열은 `file://`에서도 IndexedDB가 동작하는 것을 확인했습니다.
> 다만 위 한계들은 그대로입니다.

### 동작

```
① 폴더 열기 → 폴더 안에 jdr-index.json 이 있는가?
      있음 → 그것만 읽고 헤더 훑기를 건너뜀 (파일 1개만 읽음)
      없음 → 브라우저 캐시 → 그것도 없으면 헤더 직접 읽기
② 캘린더 하단 [인덱스 파일 내보내기] → 다운로드
③ 그 파일을 폴더에 복사해 두면 이후로는 자동 인식
```

브라우저는 폴더에 직접 쓸 수 없어서 내보내기는 다운로드로 합니다.
한 번만 복사해 두면 됩니다.

### 측정 (680개 파일)

| 방식 | 소요 | 실제로 여는 파일 수 |
|---|---|---|
| 최초 (헤더 프로브) | 1.60초 | **680개** |
| 브라우저 캐시 | 0.45초 | 0개 |
| **인덱스 파일** | **0.42초** | **1개 (78.9 KB)** |

이 환경은 SSD라 차이가 작지만, **모바일에서 70MB 파일 828개를 여는 오버헤드**가
크다면 이득이 훨씬 큽니다. 인덱스 파일은 828번이 아니라 **1번** 열면 되기 때문입니다.
실제 828개 폴더의 인덱스는 약 96KB로 예상됩니다.

### 안전장치

- 항목마다 **크기와 수정 시각**을 함께 저장합니다. 하나라도 다르면 그 파일만 다시 읽습니다
  (루프 녹화로 덮어써진 파일을 오래된 인덱스로 잘못 읽지 않습니다)
- 인덱스 파일이 깨졌거나 형식이 다르면 **사유를 화면에 알리고** 직접 읽기로 넘어갑니다
- 원본 JDR은 건드리지 않습니다
- 행 하나가 한 줄인 JSON이라 사람이 열어볼 수 있고, diff도 됩니다 —
  "이 폴더에 무엇이 언제 있었는지"의 기록으로도 쓸 수 있습니다

## 13. 실기기 피드백 반영 (2차)

실제 기기(갤럭시 / 스냅드래곤 8 Elite Gen 5 / Android 17)에서 받은 피드백입니다.

### ① 재생 끊김 — 원인은 디코딩이 아니라 읽기 횟수였습니다

8 Elite Gen 5라면 720p 2채널 디코딩은 여유입니다. 실제 파일로 읽기 패턴을 계측했습니다.

```
69초 영상 1개(70MB) 재생 → 파일 읽기 4,190회 (평균 16.8KB), 초당 약 60회
```

프레임마다 `Blob.slice().arrayBuffer()`를 호출하고 있었습니다. 데스크톱에서는 티가
안 나지만 모바일에서는 호출마다 파일시스템을 거치므로 그대로 끊김이 됩니다.

**읽기 버퍼링**을 넣었습니다. 프레임은 파일 안에서도 순서대로 놓여 있으므로
4MB씩 미리 읽어두면 대부분 메모리에서 해결됩니다.

| | 파일 읽기 호출 |
|---|---|
| 이전 | **4,190회** |
| 지금 | **18회** (메모리 적중 4,184회) |

**233분의 1**입니다. 채널 0과 1이 번갈아 나와도 같은 덩어리 안에 있어 함께 적중합니다.

함께 조정한 것:

- `optimizeForLatency: true` → **false**. 파일 재생에서는 저지연보다 고른 처리량이
  중요한데, true면 디코더가 버퍼링을 거의 하지 않아 프레임이 튑니다
- `hardwareAcceleration: 'prefer-hardware'` (지원 안 되면 지정 없이 재시도)
- 캔버스 컨텍스트에 `desynchronized: true`
- 크기가 같으면 `drawImage`에 스케일 인자를 주지 않음
- 디코더 큐 12 → 16, 렌더 대기열 8 → 6
- 화면이 가려지면 자동 일시정지 (배터리)

**진단 수단**: `?debug=1`로 열면 재생 화면에 초당 디코딩·렌더·버린 프레임 수가
표시됩니다. 여전히 끊긴다면 이 숫자로 원인을 좁힐 수 있습니다.

### ② 구간 전환 시 회색 잔상

`activate()`가 다음 구간을 파싱하는 동안(수십~수백 ms) 이전 프레임이 캔버스에
그대로 남아 있었습니다. 전환을 시작하는 즉시 캔버스를 검게 지우고
"여는 중…"을 표시하도록 고쳤습니다.

또 `init()`이 매번 `canvas.width`에 대입하고 있었는데, 이 대입 자체가 캔버스를
지우므로 크기가 같아도 깜빡였습니다. 실제로 달라질 때만 바꿉니다.

### ③ 지도 배율·위치가 리셋됨

구간이 바뀌거나 GPS 스캔이 진행될 때마다 `fitBounds`를 호출하고 있었습니다.
**처음 한 번만** 맞추고, 이후에는 사용자가 보던 위치를 유지합니다.
다시 전체를 보고 싶으면 지도 아래 **[전체 경로 보기]** 버튼을 씁니다.

### ④ 같은 날짜의 다른 시간대로 가려면 캘린더까지 돌아가야 했음

재생 화면 타임라인 위에 **운행 칩**을 넣었습니다.

```
[09-12 전체 20개]  [08:09~08:55 12개]  [22:24~23:10 8개]
```

캘린더로 돌아가지 않고 바로 옮길 수 있습니다.

## 14. 실기기 피드백 (3차)

### ① 센서 범례가 좌우로 흔들림

값이 `0.008` → `0` → `1` 처럼 자릿수가 바뀌면서 항목 위치가 밀렸습니다.

- 값 형식을 **고정 자릿수**로 (G센서 소수 3자리, 속도 1자리)
- 값 칸 폭을 **`min-width`가 아니라 `width`로 고정** — min-width로는 음수 부호가
  붙는 순간(`-0.051`) 한 자가 늘어나 그대로 밀립니다

실측: 재생 위치를 10번 옮기며 범례 항목의 좌표를 재본 결과,
모바일(390px)·데스크톱(1280px) 모두 **위치 변화 1종류**(전혀 흔들리지 않음)입니다.

### ② 영상 저장이 느림

프레임마다 Blob 조각을 만들고 있었습니다. 3,545프레임이면 조각이 3,545개고,
Blob을 만들 때 그만큼 복사가 일어납니다. 게다가 루프가 화면에 양보하지 않아
진행률조차 갱신되지 않았습니다(멈춘 것처럼 보임).

- 8MB씩 모아 넘기는 수집기로 바꿔 조각을 **3,545개 → 5개 남짓**으로
- **80ms마다 화면에 양보** (시간 기준이라 기기가 달라도 일정)
- 진행률을 프레임 수가 아니라 **바이트 기준**으로

실측(70MB 파일, 전방 34.4MB): **2.1초 · 16MB/s**, 진행률이 17단계로 갱신되어
화면이 멈추지 않습니다.

### ③ 영상은 끝났는데 시간이 계속 커짐 (`1:10.7 / 1:08.9`)

**헤더에 적힌 종료 시각(+0xA4)이 실제 마지막 패킷보다 1.8초 일렀습니다.**
표시 길이는 헤더 기준, 실제 재생은 패킷 기준이라 넘어간 것입니다.

이건 표시만의 문제가 아니었습니다. 파일 사이마다 1.8초씩 어긋나
**없는 빈 구간이 생기고** 타임라인이 빗금투성이가 됩니다.

- 재생 길이 표시를 **실제 재생 중인 문서 기준**으로 통일
- 프로브에서 헤더 종료 시각과 **마지막 패킷 시각을 대조해 더 늦은 쪽**을 사용
  (읽기 2회 추가 — 파일당 2회 → 5회, 660개 1.6초 → 2.6초. 정확성이 우선)
- 계산이 바뀌었으므로 **인덱스 파일 v1과 기존 브라우저 캐시는 버립니다**
  (v1 인덱스를 만나면 사유를 알리고 다시 읽습니다 — 다시 내보내 주세요)

## 15. 4차 실기기 피드백 — 끊김 악화와 버튼 잔상

### ① "이전 버전보다 더 끊겨" — 제가 만든 회귀입니다

3차 피드백의 "끊김 최적화"에서 넣은 세 가지 중 **둘이 거꾸로**였습니다.

| 바꾼 것 | 의도 | 실제 |
|---|---|---|
| `PENDING_MAX` 8 → 6 | GPU 메모리 절약 | 렌더 대기열이 얇아져 지터를 못 버팀 |
| `optimizeForLatency: false` | 고른 처리량 | 디코더가 출력을 미뤄 프레임이 늦게 나옴 |
| 읽기 버퍼 4MB 동기 대기 | 읽기 횟수 감소 | 미스 한 번의 대기가 김 |

앞의 둘은 되돌렸습니다(`PENDING_MAX = 14`, `optimizeForLatency: true`).
블랙박스 H.264에는 B프레임이 없어 재정렬이 필요 없으므로 저지연 모드가 맞습니다.

세 번째는 "작게 자르고 미리 당기자"(1MB × 10 + 선행 읽기)로 고쳤는데,
**측정이 그 추론을 반박했습니다.** 인공 지연을 넣고 600프레임을 돌린 결과:

| 설정 | 느린 저장소(20ms/회, 60MB/s) | 더 느린 저장소(40ms/회, 30MB/s) |
|---|---|---|
| 4MB × 6 + 선행 읽기 | 미스 5회 · 대기 433ms · 읽기 11회 | 미스 5회 · 대기 868ms · 읽기 11회 |
| 4MB × 3, 선행 읽기 없음 | 미스 5회 · 대기 436ms · 읽기 11회 | 미스 5회 · 대기 869ms · 읽기 11회 |
| 1MB × 10 + 선행 읽기 | 미스 19회 · 대기 692ms · 읽기 39회 | 미스 19회 · 대기 1394ms · 읽기 39회 |

작게 자르면 **미스 한 번의 대기는 짧아지지만 미스 자체가 4배**가 됩니다.
채널 0·1이 번갈아 나오므로 창이 넉넉해야 양쪽이 같은 덩어리를 씁니다.
→ **4MB × 6 + 선행 읽기**로 확정했습니다(최선과 동률이면서 선행 읽기도 유지).

단, 시뮬레이션은 실기기의 저장소 특성을 재현하지 못합니다.
그래서 `?debug=1`에 **읽기 대기 ms·미스 횟수**를 초당으로 띄웁니다.
대기가 크면 읽기가, 버림이 크면 디코딩이 원인입니다.

### ② 버튼 바탕이 회색으로 굳음

`:hover`에 배경색을 준 게 원인입니다. 안드로이드 크롬은 한 번 누른 요소를
**다른 곳을 누를 때까지 계속 hover로 취급**합니다. 흰색 → 회색까지는 가는데
회귀가 없습니다. 재생/일시정지 버튼도 같은 이유였습니다.

- hover 규칙 전부를 `@media (hover: hover) and (pointer: fine)` 안으로
- 터치에는 손을 대고 있는 동안만 유지되는 `:active`로 누름 표시
- `-webkit-tap-highlight-color: transparent` — 탭할 때 뜨는 회색 사각형 제거
- 스타일시트에 hover 규칙이 새로 새어 나오면 테스트가 잡습니다

## 16. 인덱스 증분 동작 정리

**질문: 새 영상이 추가되면 그 파일만 인덱스에 붙나?**

파일 단위로는 그렇습니다. 파일 하나씩 세 단계로 떨어집니다.

```
① 인덱스 파일에 있고 크기·수정시각이 같다  → 그대로 씀 (읽기 0회)
② 브라우저 캐시(IndexedDB)에 있다        → 그대로 씀 (읽기 0회)
③ 둘 다 없다                          → 헤더를 직접 읽음 (파일당 5회)
```

`indexMatches()`는 크기와 수정 시각을 함께 봅니다. 660개 중 12개가 새로 생겼으면
그 12개만 읽고, 덮어써진 파일이 있으면 그 파일만 다시 읽습니다.

다만 두 가지가 빠져 있어 고쳤습니다.

### ① 인덱스 파일이 있으면 브라우저 캐시를 건너뛰고 있었습니다

```ts
const cached = indexMap.size > 0 ? new Map() : await probeCache.getMany(keys);
```

인덱스는 **내보낸 시점에 멈춰 있습니다.** 그 뒤에 녹화된 파일은 인덱스에 없는데
캐시까지 건너뛰니, 그 파일들을 **열 때마다** 다시 읽었습니다.
→ 인덱스가 있어도 캐시를 항상 같이 봅니다. 새 파일도 두 번째 열기부터 읽기 0회입니다.

### ② 인덱스가 낡았다는 사실을 알리지 않았습니다

브라우저는 폴더에 직접 쓸 수 없으므로 인덱스 갱신은 사용자가 눌러야 합니다.
그런데 눌러야 한다는 걸 알 방법이 없었습니다.

- 인덱스에 없던 파일 수(`missingFromIndex`)를 세어 캘린더에 경고로 띄우고,
  저장 버튼을 강조합니다
- 저장은 델타가 아니라 **전체를 다시 씁니다** — 기존 + 새 파일이 한 파일로 나옵니다
- 저장 직후 경고를 거둡니다

### ③ 용어 — "내보내기"가 아니라 "저장"

"내보내기"는 다른 곳에서 쓰려고 **다른 형식으로 뽑아내는** 동작에 쓰는 말입니다.
인덱스는 이 앱이 쓰려고 만드는 것이므로 사용자가 보기엔 그냥 저장입니다.
영상/CSV 추출 탭은 파생물을 만드는 것이 맞으므로 "내보내기"를 그대로 둡니다.

- 버튼: `인덱스 저장 (jdr-index.json)` / 낡았을 때 `인덱스 다시 저장 (...)`
- 다만 브라우저는 폴더에 직접 쓸 수 없습니다. "저장"이라고만 하면 제자리에
  저장된 것처럼 오해하므로, **다운로드 폴더에 저장되니 이 폴더로 옮기라**고
  안내 문구에 명시합니다
- 코드도 맞춰 `saveIndexFile` / `onSaveIndex` / `#btn-save-index`로 바꿨습니다

비용: 인덱스 적중 파일에 대해 IndexedDB 조회 1회가 늘어납니다(일괄 조회 한 번).
