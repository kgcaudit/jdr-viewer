# 음성 대사록(화자분리 전사) 계획안

**결정이 필요한 항목은 D13~D16입니다.**

먼저 분명히 해 둘 것이 있습니다. 이 기능은 지금까지의 작업과 성격이 다릅니다.
**제가 확인해 줄 수 없는 부분이 큽니다.**

- 이 작업 환경은 **모델 저장소(huggingface.co)와 CDN 접근이 차단**되어 있습니다.
  모델을 내려받아 실제로 돌려 볼 수 없습니다 (직접 확인: `connect_rejected`).
- 실제 블랙박스 녹음이 없습니다. 제가 가진 건 제가 만든 합성 파일뿐이라
  **실제 차내 음성의 잡음 수준을 재 볼 수 없습니다.**

아래 수치는 전부 공개된 벤치마크와 사양에서 가져온 것이고,
실제 성능은 기기에서 직접 확인해야 합니다.

## 1. 현실 점검 — 원본 신호의 한계

이게 이 기능의 전부를 좌우합니다.

| 항목 | 값 | 의미 |
|---|---|---|
| 표본율 | **8,000 Hz** | 4kHz 위 주파수가 **애초에 없음** |
| 채널 | **모노 1채널** | 방향으로 화자를 가를 단서가 없음 |
| 비트 | s16le | 문제 없음 |
| 환경 | 차내 (노면·풍절·엔진) | 광대역 잡음이 음성 대역을 덮음 |

### 왜 이게 큰 문제인가

**① 요즘 음성 모델은 전부 16kHz 학습입니다.** Whisper는 입력을 무조건
16kHz로 맞춰 넣습니다. 8kHz를 올려 봐야 **없던 정보가 생기지는 않습니다** —
"4kHz 위 주파수가 존재하지 않는 녹음에서 그걸 복원하는 게 어려운 것"이고,
신경망 복원(VoiceFixer 등)은 사람 귀에는 좋아져도 **WER은 오히려 나빠집니다**
(음향 모델이 쓰는 스펙트럼 구조를 망가뜨립니다).

**② 화자 임베딩은 더 심합니다.** 화자분리의 핵심인 화자 임베딩 모델
(wespeaker ResNet34 등)은 16kHz 학습이고, **8kHz 전화 음성에서 성능이
크게 떨어지는 것이 알려져 있습니다.** 화자를 가르는 단서 상당수가
4kHz 위에 있기 때문입니다.

### 한국어 WER (공개 벤치마크, **깨끗한 낭독 음성 · 16kHz**)

| 모델 | FLEURS | Zeroth | 크기(q8 기준 대략) |
|---|---|---|---|
| whisper-tiny | 35.4% | 47.8% | ~40MB |
| whisper-base | 27.2% | 43.6% | ~80MB |
| whisper-small | 19.6% | 28.0% | ~250MB |
| whisper-medium | 16.2% | 21.8% | ~800MB |

Whisper 학습 데이터 68만 시간 중 비영어가 17%, 그걸 98개 언어가 나눠 가지니
한국어 몫은 아주 작습니다.

**여기에 8kHz + 차내 잡음이 더해집니다.** 위 표는 바닥값입니다.
제 예상으로는 실제 체감이 **표의 1.5~2배 WER**입니다.
tiny/base는 사실상 못 쓰고, small이 되어야 "무슨 얘기였는지 짐작" 수준입니다.

> **그래서 이 기능의 목표를 "정확한 녹취록"이 아니라
> "말한 구간을 찾아 주는 색인"으로 잡기를 권합니다.** 뒤에서 다시 말씀드립니다.

## 2. 어디서 인식할 것인가 — 세 갈래

### ㉮ 브라우저 안에서 ONNX 모델 (transformers.js)

Whisper ONNX + pyannote-segmentation-3.0을 브라우저에서 돌립니다.
`device: 'webgpu'`로 GPU를 쓸 수 있고, 실제로 동작하는 공개 예제가 있습니다.

- 음성은 **기기 밖으로 나가지 않습니다** ("🔒 업로드 없음" 유지)
- 대신 **모델과 런타임을 내려받아야** 합니다
  - onnxruntime-web WASM: WebGPU 기본 빌드 **약 20MB** (최적화 8MB, 최소 3MB)
  - Whisper small q8: **약 250MB**
  - pyannote-segmentation-3.0: 약 6MB
  - 화자 임베딩(wespeaker ResNet34): 약 26MB
- 첫 실행에 **300MB 내려받기**. 이후 브라우저 캐시.
- **단일 HTML 파일 / `file://`에서는 못 씁니다.** CDN 접근이 필요합니다.

### ㉯ Chrome 기기 내장 음성 인식 (Web Speech API)

Chrome에 **기기 안에서 처리하는** 음성 인식이 들어왔습니다.
`SpeechRecognition.available({ processLocally: true, langs: ['ko-KR'] })`로
확인하고, `install()`로 언어팩을 받습니다.

그리고 결정적으로 — **마이크가 아니라 오디오 트랙을 넣을 수 있습니다.**

```js
const dest = audioContext.createMediaStreamDestination();
recognition.processLocally = true;
recognition.start(dest.stream.getAudioTracks()[0]);   // 실험적 기능
```

우리가 이미 만들어 둔 재생 그래프를 그대로 물리면 됩니다.

- **내려받을 모델이 0입니다.** 언어팩은 OS/Chrome이 관리합니다
- 구글의 한국어 기기내 모델은 Whisper small보다 나을 가능성이 높습니다
- 하지만:
  - **화자분리가 전혀 없습니다** (글자만 나옵니다)
  - **실시간 속도로만 먹습니다** — 3시간 운행이면 3시간
  - **실험적 기능**입니다. 안드로이드 Chrome 지원 여부가 불확실하고,
    142.0.7403.0 전까지는 회귀로 꺼져 있었습니다
  - 단어 단위 정밀 시각이 안 나와, 우리가 넣어 준 시점으로 역산해야 합니다

### ㉰ 내보내서 PC에서 (기존 워크플로우 연계)

앱은 **말한 구간만 잘라낸 WAV + 시각 대조표**를 내보내고,
전사는 이미 쓰고 계신 whisper-large-v3-int8 흐름에서 합니다.

- **품질이 가장 좋습니다** (large-v3는 위 표의 medium보다도 위)
- 브라우저에서 내려받을 것이 0, `file://`에서도 동작
- 대신 앱 안에서 바로 보이지는 않습니다 (왕복이 필요)

## 3. 화자분리는 실제로 무엇을 하는가

"화자분리"는 한 덩어리가 아니라 **네 단계**입니다. 어디까지 할지가 결정 사항입니다.

```
① VAD        말/침묵 가르기           Silero VAD, 약 2MB, 8kHz 원생 지원
② 분할       화자가 바뀌는 지점 찾기    pyannote-segmentation-3.0, 약 6MB
③ 임베딩     구간마다 화자 특징 벡터    wespeaker ResNet34, 약 26MB, 256차원
④ 군집       같은 화자끼리 묶기         응집 군집 (코사인 유사도)
```

**②만으로는 부족합니다.** pyannote-segmentation-3.0은 10초 창 안에서
"지금 몇 명이 말하는가"를 낼 뿐, **창을 넘어선 화자 동일성은 모릅니다.**
"이 사람이 아까 그 사람"을 알려면 ③④가 필요합니다.

그리고 ③이 8kHz에서 가장 많이 망가지는 단계입니다.

**차 안이라는 조건은 오히려 유리한 면도 있습니다.** 화자가 보통 2~3명으로
적고, 자리가 고정되어 목소리 특성이 잘 안 변합니다.
**화자 수를 사용자가 지정**하면(예: "2명") 군집이 훨씬 안정됩니다.

## 4. 제안 — 단계로 나눠 가치가 확실한 것부터

### 1단계: "말한 구간" 찾기 (VAD만)

**이것만으로 실무 가치의 대부분이 나온다고 봅니다.**

3시간 운행에서 사람이 말한 건 4분일 수 있습니다. 지금은 그 4분을 찾으려면
3시간을 훑어야 합니다. VAD는 그걸 없앱니다.

- 타임라인 스트립에 **대화 구간 띠**를 겹쳐 그립니다
- 즐겨찾기처럼 **말한 구간 목록**에서 눌러 바로 이동
- 전사가 틀려도 이 기능은 틀리지 않습니다 (있다/없다뿐)
- Silero VAD는 **8kHz를 원생 지원**하고 2MB입니다. 업샘플링 손실이 없습니다
- 모델 없이 순수 JS로 하는 길도 있습니다 (하모닉 구조 + 대역 에너지비).
  노면 잡음에서는 Silero보다 떨어지지만 **내려받을 것이 0**입니다

### 2단계: 전사 (글자)

1단계가 찾아 준 구간**만** 인식에 넣습니다. 3시간이 아니라 4분이므로
㉯(실시간 제약)도 현실적이 되고, ㉮도 훨씬 빨라집니다.

### 3단계: 화자 나누기

2단계 결과 위에 ③④를 얹습니다. 화자 수를 사용자가 지정합니다.
**여기가 8kHz의 벽에 가장 세게 부딪히는 곳**이라, 1·2단계 결과를 보고
할지 말지 다시 정하는 편이 낫다고 봅니다.

## 5. 비용 — 읽기가 제일 큽니다

간과하기 쉬운 부분입니다. 오디오는 파일 곳곳에 흩어진 AD 패킷이라,
**오디오만 뽑으려 해도 파일 전체를 읽어야 합니다.**

| 범위 | 읽을 양 | 오디오 양 | 읽기 시간(60MB/s 가정) |
|---|---|---|---|
| 현재 구간 1개 | 70MB | 1.1MB | 약 1.2초 |
| 운행 1개 (60개 파일) | 4.2GB | 66MB | 약 70초 |
| 하루 (155개 파일) | 10.8GB | 170MB | 약 3분 |

→ **기본 단위를 "현재 구간"으로,** 운행 전체는 사용자가 명시적으로
누를 때만 돌리는 게 맞습니다.

## 6. 증거로서의 원칙

감사 도구라는 성격상 이건 양보하면 안 된다고 봅니다.

- **자동 전사는 증거가 아니라 색인입니다.** 화면에 그렇게 씁니다
- 모든 줄은 `파일명 · 파일 내 시각 · 절대 시각`을 답니다
- 줄을 누르면 **그 지점 음성이 바로 재생됩니다** — 사람이 귀로 확인할 수 있어야
  틀린 전사도 쓸모가 있습니다
- 화자는 `화자 A/B`로만 적습니다. 사람 이름을 자동으로 붙이지 않습니다
- 신뢰도가 낮은 줄은 흐리게 표시합니다

## 8. 제 권고

**D13은 ㉱ + ㉰, D14는 Silero, D15는 보류입니다.**

이유는 하나입니다. **8kHz 모노 차내 음성이라는 원본 조건이 나쁩니다.**
브라우저에 300MB를 들여 whisper-small을 얹어도 한국어 WER이 30~40%면
"녹취록"이라 부를 수 없습니다. 반면 **VAD는 원본 조건이 나빠도 잘 됩니다**
— 있다/없다만 가르면 되고, Silero는 8kHz를 원래 지원합니다.

그래서:
1. **VAD로 "말한 구간"을 찾아 타임라인에 얹습니다.** 확실한 가치입니다
2. 그 구간만 잘라 **PC 워크플로우로 내보냅니다.** 품질은 large-v3가 냅니다
3. 브라우저 전사(㉮/㉯)는 **실제 녹음으로 한 번 재 보고** 결정합니다 —
   표본 하나만 주시면 제가 예상 품질을 가늠해 볼 수 있습니다

다르게 보신다면 말씀해 주세요. 특히 "왕복 없이 앱 안에서 끝나야 한다"가
중요하시면 ㉯(Chrome 기기내)부터 시험해 보는 것도 합리적입니다 —
내려받을 게 없어서 실패해도 잃는 게 없습니다.

## 9. 1단계 구현 결과 — 말한 구간 찾기

결정을 맡겨 주셔서 권고안대로 1단계를 넣었습니다. **다만 D14는 바꿨습니다.**

### D14를 Silero가 아니라 순수 JS로 한 이유

계획안에서는 Silero(2MB)를 권했는데, 쓰다 보니 앞뒤가 안 맞았습니다.
Silero를 쓰려면 **ONNX 런타임(최소 3MB, 기본 20MB)을 실행 시점에 내려받아야**
하고, 그러면 지금까지 지켜 온 **단일 HTML 파일 · 오프라인 동작**이 깨집니다.
매번 파일 하나를 받아 폰에서 여는 방식이 이 앱의 전제인데,
VAD 하나 때문에 그걸 버리는 건 맞바꿈이 나쁩니다.

그래서 차내 잡음의 성질을 직접 이용했습니다.

```
노면·엔진·풍절음 = 넓은 대역에 퍼진 거의 일정한 소리
사람 목소리      = 300~3400Hz에 몰린 하모닉 + 음절마다 끊김(2~8Hz)
```

세 가지를 재서 곱합니다 (하나라도 아니면 0이 되도록).

| 신호 | 무엇을 보는가 |
|---|---|
| 대역 SNR | 음성 대역이 **적응형 잡음 바닥**(3초 창의 하위 20%)보다 얼마나 솟았나 |
| 하모닉 | 자기상관 최대값 — 성대의 주기성. 노면 잡음에는 없다 |
| 출렁임 | 2~8Hz 음절 속도로 에너지가 오르내리나. **일정한 잡음을 가장 잘 거른다** |

그 위에 히스테리시스(들어갈 때 엄하게·나올 때 느슨하게), 짧은 것 버리기(0.35초),
숨 쉬는 사이 잇기(0.4초), 앞뒤 여유(0.2초)를 얹었습니다.

### 측정

실제 녹음이 없어 **차내 소리를 흉내내 만든 신호**로 쟀습니다
(저역이 강한 광대역 잡음 + 150Hz 하모닉 8배음 + 초당 4음절 포락선).

| 확인한 것 | 결과 |
|---|---|
| 노면 잡음만 20초 | 0곳 (오검출 없음) |
| 주차(거의 무음) 20초 | 0곳 |
| 짧은 충격음(문 닫힘·경적) | 0곳 — 말로 세지 않음 |
| 잡음 속 말 한 마디 | 찾음 |
| 떨어진 두 마디 | 각각 찾음 |
| 0.2초 끊김 | 한 구간으로 이음 |
| 5초 끊김 | 두 구간으로 나눔 |

**잡음 한계도 기록해 뒀습니다.** 목소리 세기를 0.5로 고정하고 잡음을 올리면:

```
잡음 0.05 찾음 · 0.1 찾음 · 0.2 찾음 · 0.4 놓침
```

실기기 녹음으로 이 문턱을 다시 잡아야 합니다. 흉내는 흉내일 뿐입니다.

### 화면

- **"대화" 탭**이 생겼습니다. 지금 보고 있는 구간을 훑습니다
  (70MB 파일 하나 ≈ 1.2초). 결과는 구간별로 기억해 다시 읽지 않습니다
- 목록의 줄을 누르면 **그 지점으로 바로 재생 이동**합니다
- 타임라인 스트립 위에 **말한 구간 띠**(노란 줄)가 겹쳐집니다
- 신뢰도는 숫자가 아니라 **막대**로만 보여 줍니다 — 숫자로 적으면

### 내보내기 — PC 전사 흐름으로 넘기는 입구

- `*_speech.wav` — 침묵을 뺀 음성만 이어붙인 것
- `*_speech.csv` — **대조표**. WAV의 몇 초가 원본의 어느 파일 몇 초였는지

```
wav_start_s,wav_end_s,source_file,file_start_s,file_end_s,recorded_at,duration_s,score
0.000,3.400,data/00000460.jdr,6.800,10.200,2026-09-08T08:09:26.800Z,3.400,0.612
```

이 짝이 있으면 whisper-large-v3 전사 결과를 원본으로 되짚을 수 있습니다.
대조표 없이 잘라낸 음성만 넘기면 증거로 못 씁니다.
