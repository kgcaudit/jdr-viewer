# 영상은 이어지는데 왜 빈 구간이 생기나 — 블록 체인 추적의 결함

> 보고(실기기 화면): 구간 22개 · 벽시계 30분 13초 · **실제 영상 24분 45초(81.9%)**
> · **빈 구간 18곳 · 합계 5분 26초**. "주행은 계속했고 영상도 계속 녹화된 것
> 같은데 왜 끊겨 있나?"

22개 파일에 경계는 21곳인데 그중 **18곳**에 빈 구간이 있다. 어쩌다 한둘이
아니라 거의 모든 경계다. 이런 모양은 "가끔 일어나는 일"이 아니라 **체계적인
계산 오류**를 가리킨다.

## 찾은 것 — 우리 코드가 참고 구현과 다르게 동작한다

JDR 한 파일 안에는 JEB1 블록이 여러 개 들어 있다. 블록을 어떻게 찾느냐에서
두 구현이 갈린다.

**참고 구현 (파이썬 도구, 실기기 파일로 역분석한 것)** — 파일 전체에서
매직을 찾는다. 어디에 있든 빠뜨리지 않는다.

```python
def find_jeb_headers(buf) -> list[int]:
    while True:
        i = buf.find(JEB_MAGIC, pos)      # 파일 전체를 훑는다
        if i < 0: break
        ...
        headers.append(i)
```

**우리 프로브 (`core/segment.ts`)** — 다음 블록의 자리를 **계산해서** 따라간다.
그리고 계산한 자리에 헤더가 없으면 **거기서 멈춘다.**

```ts
const next = h.indexOffset + h.packetCount * INDEX_ENTRY_SIZE;
pos = next > pos ? next : -1;
// ...
const h = await validateHeader(src, pos);
if (!h) break;        // ← 여기서 그 뒤의 블록을 전부 잃는다
```

"인덱스 테이블 바로 뒤에 다음 블록이 붙는다"는 전제는 대개 맞지만, 기기가

- 블록을 **섹터 경계에 맞추려 패딩**을 넣거나,
- 블록 하나를 **쓰다 말았거나**,
- 그 자리의 헤더가 검증을 통과하지 못하면

그 전제가 깨진다. 그러면 `break` 한 줄로 **파일 뒷부분을 통째로 못 본다.**

## 왜 그게 "빈 구간"으로 보이나

파일의 끝 시각은 마지막 블록의 마지막 패킷에서 구한다. 뒷블록을 잃으면
끝 시각이 그만큼 **이르게** 나온다. 그러면

1. 그 파일이 실제보다 짧아 보이고,
2. 다음 파일의 시작 시각과의 사이가 벌어져 **없는 빈 구간이 생기고**,
3. 파일마다 똑같이 일어나므로 **경계마다** 생긴다.

보고된 수치와 정확히 맞는다 — 81.9%만 영상으로 잡히고, 21곳 중 18곳이 비었다.

더 나쁜 건 **재생도 같이 짧아진다**는 점이다. 폴더에서 열면 파서가 프로브가
넘겨준 블록 목록을 그대로 쓰기 때문이다(전체 훑기를 건너뛰려고 그렇게 만들었다).

```ts
candidates = needScan ? r.candidates : options.blockOffsets!;   // ← 프로브의 목록
```

즉 **한 군데의 결함이 타임라인·탐색·재생 길이·내보내기에 모두 번진다.**
단일 파일로 열면(`파일` 버튼) 파서가 직접 전체를 훑으므로 이 증상이 없다 —
폴더로 열 때만 생긴다. 같은 파일이 여는 방법에 따라 길이가 달라 보였다면
그게 이 결함의 지문이다.

## 고침

체인이 끊긴 자리에서 멈추지 않고 **앞으로 훑어 다음 블록을 따라잡는다.**
참고 구현과 같은 결과에 이르되, 프로브의 존재 이유(파일당 몇 KB만 읽기)는
지킨다.

- 정렬 패딩이 있을 만한 **4KB부터** 본다. 대개 여기서 끝난다.
- 없으면 64KB → 256KB로 넓히되, **넓히는 건 파일당 4번까지만**. 뒤에
  쓰레기가 붙은 파일 하나 때문에 폴더 전체가 느려지면 안 된다.
- 그래도 못 찾으면 포기하고 **얼마나 읽었는지를 기록한다.**

## 그래서 얼마나 읽었나 — 숫자로 내놓는다

조용히 짧아지는 게 이 결함의 가장 나쁜 점이었다. 그래서 요약 탭에
**"파일 읽힌 정도"** 를 넣었다.

- `100.0% — 파일 끝까지 읽었습니다` → 빈 구간은 우리 탓이 아니다. 진짜다.
- `81.9% — 뒷부분을 덜 읽은 파일 18개` → 빈 구간의 정체가 이것이다.

이 한 줄이면 "영상이 끊긴 것"과 "우리가 못 읽은 것"이 갈린다.

## 빈 구간을 원인별로 나눈다

남은 빈 구간도 성격이 다르다. 구간 탭에서 묶어 보여 준다.

| 묶음 | 뜻 | 대응 |
| --- | --- | --- |
| 파일이 없음 | 파일 번호가 건너뜀 | 덮어쓰기(루프 녹화)·삭제·복사 누락 |
| 파일 전환 틈 (5초 이하) | 기기가 파일을 닫고 여는 사이 | **정상.** 영상은 이어진다 |
| 번호는 이어지는데 길게 빔 | 녹화가 실제로 멈췄거나 덜 읽음 | "파일 읽힌 정도"를 먼저 확인 |
| 원인 미상 | 이름에서 번호를 못 읽음 | — |

5초 이하의 전환 틈을 "파일 없음"과 같이 세면 사람이 잘못 판단한다.
숫자 하나로 뭉뚱그리지 않는 이유다.

## 인덱스를 다시 읽어야 한다

이미 저장된 인덱스와 브라우저 캐시에는 **잘린 블록 목록과 이른 종료 시각이
굳어 있다.** 그래서

- 인덱스 파일 형식을 v4로 올렸다 (v3 이하는 다시 읽는다)
- 브라우저 캐시 DB도 4로 올려 통째로 버린다

쓰던 폴더는 **인덱스 갱신** 을 한 번 눌러 다시 만들고 저장하면 된다.

## 시험

`test/folder.test.ts`

- 블록 사이에 2KB 패딩을 끼운 파일 → 두 블록을 다 찾고 길이가 온전하다
  (고치기 전 코드로는 절반 길이가 되어 실패한다)
- 되찾기 범위를 넘는 경우 → 조용히 짧아지지 않고 `coveredBytes`에 남는다
- 뒤에 자투리가 붙은 파일 → 읽는 양이 16KB를 넘지 않는다 (프로브가 느려지면 안 된다)

## 아직 확인이 필요한 것

이 결함은 코드에서 **증명**했고 시험으로 고정했지만, 보고된 그 폴더의 빈 구간이
**전부** 이것 때문인지는 실기기 파일로 확인해야 한다. 갱신 후 "파일 읽힌 정도"가
100%인데도 빈 구간이 남는다면, 남은 건 위 표의 다른 묶음이다.
