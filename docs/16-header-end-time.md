# 주차 다섯 시간이 "녹화됨"으로 덮이던 결함

> 보고(실기기 화면): `00000224.jdr` 한 구간이 **5시간 35분 · 70.0 MB**.
> 10:25에 주행이 끝나고 16:01에 다시 시작했는데 그 사이가 빈 구간이 아니라
> **이어진 것으로** 표시된다. 하루 84개 파일이 09:56~07:54 한 운행으로 묶였다.

## 화면이 이미 답을 말하고 있었다

같은 목록의 다른 줄과 견주면 한 줄만 다르다.

```
00000223.jdr  10:25:04   data · 49초      · 70.0 MB · 시각출처 패킷
00000224.jdr  10:25:54   data · 5시간 35분 · 70.0 MB          ← 꼬리표가 없다
00000225.jdr  16:01:39   data · 47초      · 70.0 MB · 시각출처 패킷
```

- **크기가 똑같이 70.0 MB다.** 5시간 35분을 담았다면 다른 파일의 400배여야 한다.
  담긴 영상은 다른 파일과 같은 50초 남짓이다.
- **`시각출처 패킷` 꼬리표가 없다.** 이 줄만 시각을 **헤더에서** 가져왔다는 뜻이다.
- 10:25:54 + 5시간 35분 = **16:01** — 다음 파일이 시작한 바로 그 시각이다.

즉 이 파일의 종료 시각으로 **다음 시동을 건 시각**이 들어와 있었다.

## 원인 — 종료 시각만 한쪽으로 봐줬다

시작 시각은 이미 "첫 패킷이 기준"으로 고쳐 두었다. 그런데 종료 시각은
**헤더보다 늦을 때만** 패킷을 쓰고 있었다.

```ts
} else if (Number.isFinite(fromPackets.endMs) && fromPackets.endMs > endMs) {
  endMs = fromPackets.endMs;   // ← 늦을 때만 바로잡는다
  timeSource = 'packets';
}
```

이렇게 만든 이유는 있었다. 헤더의 종료 시각(+0xA4)이 실제 마지막 패킷보다
**이르게** 적히는 경우를 실기기에서 확인했고(1.8초), 그걸 바로잡으려던 것이다.
그런데 반대 방향은 막지 않았다. 헤더에는 기기가 그 파일을 **마지막으로 손댄
시각**이 적히는 일이 있다. 주차로 세워 두었다가 시동을 걸면, 직전 주행의
마지막 파일이 그때 다시 닫히면서 종료 시각이 갱신된다.

그래서 49초짜리 파일 하나가 **5시간 35분짜리**가 되었다.

## 왜 이게 가장 나쁜 종류의 오류인가

빈 구간을 **없는 것으로 만든다.** 그 5시간 35분은 아무것도 찍히지 않은
주차 시간인데, 화면에는 "녹화된 구간"으로 칠해진다. 없는 기록을 있다고
말하는 셈이라, 감사 자료로서는 파일이 빠진 것보다 위험하다.

번지는 범위도 넓다.

- 띠에 빈 구간이 사라져 **하루가 통째로 이어진 것처럼** 보인다
- 운행 나누기(공백 10분 기준)가 안 먹혀 **84개가 한 운행**으로 묶인다
- 캘린더의 "녹화 길이"가 주차 시간만큼 부풀어 오른다
- 요약의 "실제 영상 %"가 실제보다 높게 나온다

앞서 고친 **블록 체인 결함은 반대 방향**이었다(있는 영상을 없다고 함).
두 결함이 서로를 가려 합계만 보면 그럴듯해 보였다.

## 고침

**종료도 마지막 패킷이 기준이다.** 시작과 같은 원칙이고, 한쪽만 봐주지 않는다.

```ts
if (Number.isFinite(fromPackets.endMs) && fromPackets.endMs >= startMs) {
  if (endMs !== fromPackets.endMs) timeSource = 'packets';
  endMs = fromPackets.endMs;
}
```

패킷을 못 읽어 **헤더 값을 쓸 수밖에 없을 때**를 위한 방어도 함께 넣었다.
담긴 프레임 수가 도저히 받쳐 주지 못하는 길이라면 그건 녹화 길이가 아니다.

```ts
} else if (timeSource === 'header' && frames > 1 && endMs - startMs > (frames / MIN_FPS) * 1000) {
  endMs = startMs + ((frames - 1) / 30) * 1000;
  endEstimated = true;   // 화면에 "길이 추정"으로 표시된다
}
```

`MIN_FPS`는 1로 아주 느슨하게 잡았다. 주차 저속 녹화까지 감안해도 프레임
하나에 1초를 넘게 줄 수는 없다. 60프레임짜리 파일이라면 60초까지는 믿고,
5시간은 받아들이지 않는다.

추정으로 고친 구간은 **`길이 추정` 꼬리표가 붙는다.** 조용히 고치지 않는다.

## 시험

`test/folder.test.ts`

- 헤더 종료가 5시간 35분 뒤인 파일 → 마지막 패킷을 쓴다 (49초)
- 그 파일 + 5시간 뒤 파일 → **주차가 빈 구간으로 되살아난다**
  (고치기 전에는 두 파일이 붙어 공백이 0이었다)

두 시험 모두 고치기 전 코드로는 실패한다.

## 쓰던 폴더는 인덱스를 갱신해야 한다

이미 저장된 인덱스와 브라우저 캐시에 **5시간짜리 종료 시각이 굳어 있다.**
인덱스 v5로 올려 옛 인덱스는 다시 읽게 했고, 캐시 DB도 함께 올렸다.
폴더의 `jdr-index.json`은 **인덱스 갱신 → 인덱스 저장** 으로 다시 만들면 된다.

# 2차 — 고쳐도 그대로였다. 원인은 하나 더 있었다

앞의 고침(종료도 패킷 기준)을 넣었는데 **화면이 그대로였다.** 그렇다면 앞의
추론 중 하나가 틀렸다는 뜻이다. 어디가 틀렸는지 되짚었다.

## 되짚기 — 화면이 말하던 것을 다시 읽는다

그 줄에 `시각출처 패킷` 꼬리표가 없었다는 건 `timeSource === 'header'` 라는
뜻이고, 옛 규칙(`fromPackets.endMs > endMs` 일 때만 교체)에서 그 상태가 되는
경우는 둘이다.

1. 패킷에서 읽은 끝이 **10:26:43(옳은 값)** 인데 헤더(16:01)보다 이르러 교체가
   안 된 경우 → 1차 고침으로 해결된다
2. 패킷에서 읽은 끝이 **16:01 그 자체**인 경우 → 헤더와 같으므로 교체 여부와
   무관하게 아무것도 바뀌지 않는다

**고쳐도 그대로였다는 사실이 (2)를 가리킨다.** 즉 이 파일에는 영상이 끝난 뒤
다섯 시간 반이 지난 시각의 패킷이 **실제로 들어 있다.**

기기가 시동을 걸 때 직전 파일 꼬리에 GPS·센서 패킷을 한둘 덧붙이는 것이다.
70MB에 영상은 50초뿐인데 마지막 패킷만 16:01인 이유가 이것으로 설명된다.

## 진짜 규칙 — 구간의 끝은 **내용이 끝난 곳**이다

파일에 마지막으로 적힌 무언가가 아니라, **영상·음성이 끝난 곳**이 구간의 끝이다.
이 원칙을 세 군데에 같이 넣었다.

**① 프로브 (`core/segment.ts`)** — 꼬리를 거슬러 올라가며 **영상·음성 패킷**을
먼저 친다. 인덱스 항목의 앞 4바이트가 태그라 **추가 읽기 없이** 가려낼 수 있다.

```ts
const kind = tagKind(packTag(ev.getUint8(at), …));
const isMedia = kind === TagKind.Video || kind === TagKind.Audio;
…
return { startMs, endMs: Number.isFinite(mediaEnd) ? mediaEnd : anyEnd };
```

**② 파서 (`core/parser.ts`)** — `contentEndMs`를 따로 센다. 재생 중 타임라인을
고치는 `applyRealTimes`가 `lastTimeMs`를 쓰고 있어서, **그 파일을 여는 순간
5시간이 되살아나던** 경로도 막았다.

**③ 최후의 방어선 (`durationExceedsContent`)** — 시각이 어디서 왔든,
담긴 내용이 못 받치는 길이는 믿지 않는다.

```ts
const units = Math.max(frames, packets);   // 영상이 없는 파일도 가늠한다
return durationMs > (units / MIN_RATE_PER_SEC) * 1000;   // 패킷 하나에 1초
```

주차 저속 녹화(1fps)까지 감안해도 패킷 하나에 1초를 넘게 줄 수는 없다.
1500프레임짜리 파일은 25분까지 받아들이고 5시간 35분은 받아들이지 않는다.
①이 못 막는 변형(꼬리에 덧붙은 게 **영상** 패킷인 경우 등)까지 여기서 걸린다.

## 감추지는 않는다 — 요약 탭 "꼬리 패킷"

길이를 영상 기준으로 잡되, **그런 패킷이 있다는 사실은 그대로 알린다.**
파일에 적힌 것을 화면에서 지워 버리면 그게 더 나쁜 거짓말이다.

```
종료        2026-09-05 10:26:43
길이        49초
꼬리 패킷   2026-09-05 16:01:39
            영상이 끝나고 5시간 35분 뒤에 적힌 패킷이 있습니다
            (시동을 걸며 덧붙은 기록으로 보입니다).
            구간 길이는 영상·음성 기준으로 잡습니다.
```

이 줄이 처음부터 있었다면 1차에서 바로 찾았을 것이다.

## 시험

`test/folder.test.ts`

- 꼬리에 GPS 패킷이 5시간 35분 뒤로 붙은 파일 → 구간은 49초 (①이 없으면 실패)
- 그 파일 + 다섯 시간 뒤 파일 → **주차가 빈 구간으로 되살아난다**
  (①을 꺼도 ③이 잡는 것을 확인했다)
- `durationExceedsContent` 단위 시험 — 1fps는 받아들이고 그 이상은 거른다
- 영상이 없는 파일도 패킷 수로 가늠한다
