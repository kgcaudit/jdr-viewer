# 탐색 막대가 멈추고 다음 파일로 튕기던 문제

"1분 9초짜리 영상인데 재생 막대가 14초에서 멈춰 있다. 영상과 소리는 정상이다."

**원인을 찾았고, 짐작하신 대로 파일 사이 공백과 같은 뿌리였습니다.**

---

## 1. 무슨 일이 있었나

화면에는 두 값이 함께 있습니다.

```
0:14.6 / 1:09.0     ← 글자: 실제로 재생 중인 문서 기준
[━━━━━━●━━━━━]      ← 막대: 프로브가 구한 구간 기준
```

**둘의 기준이 달랐습니다.**

| | 기준 |
|---|---|
| 재생 위치·길이 | `doc.firstTimeMs` (파일을 열어 읽은 **실제 첫 패킷**) |
| 라이브러리 구간 | `seg.startMs` / `seg.endMs` (헤더만 읽은 **프로브 값**) |

프로브의 종료 시각이 실제보다 이르면 — 예를 들어 실제 69초짜리 파일을
32초로 봤다면 — 막대를 뒤쪽으로 끌었을 때 이런 일이 벌어집니다.

```
막대 32초 → 절대 시각으로 환산 → 구간 범위(32초)를 넘어섬
          → "빈 구간이네" → 다음 파일 시작으로 건너뜀
          → 글자는 새 파일의 0:14.6, 막대는 끌어 놓은 자리 그대로
```

**막대가 멈춘 게 아니라, 막대와 글자가 서로 다른 곳을 가리키고 있었습니다.**

그리고 같은 원인이 파일 사이에 없는 빈 구간을 만듭니다.
파일이 32초로 잡히면 나머지 37초가 통째로 비어 보입니다.

---

## 2. 왜 종료 시각이 짧게 잡혔나

프로브는 **마지막 인덱스 항목이 가리키는 패킷 하나**의 시각만 읽었습니다.

그 패킷의 시각이 비었거나 깨져 있으면 종료 시각을 못 구하고,
그러면 **헤더에 적힌(실제보다 이른) 값이 그대로** 남습니다.
파일 꼬리에 시각 없는 패킷이 붙는 건 실기기에서 흔합니다.

---

## 3. 고친 것

### ① 꼬리를 되짚어 읽습니다

끝에서부터 최대 24개 인덱스 항목을 거슬러 올라가며
**시각이 읽히는 첫 패킷**을 찾습니다. 인덱스 항목은 붙어 있으므로
한 번에 읽고 패킷 헤더만 몇 번 더 봅니다. 비용은 거의 그대로입니다.

### ② 파일 안 이동은 라이브러리를 거치지 않습니다

`seekInFile()`이 "구간 시작 + 상대 위치"를 절대 시각으로 만들어
라이브러리에 되물었습니다. 이미 이 파일 안이라는 걸 아는 상황이므로
**문서 기준으로 곧장** 옮깁니다. 더 이상 다음 파일로 튕기지 않습니다.

### ③ 기준을 하나로 통일했습니다

같은 구간 안에서의 탐색도 `seg.startMs`가 아니라
**실제 문서의 첫 패킷**을 기준으로 계산합니다.

### ④ 열어 본 파일은 타임라인을 고칩니다

파일을 실제로 열면 진짜 시각을 알게 됩니다. 프로브 값과 250ms 넘게
다르면 **구간 기록을 고치고 빈 구간·겹침을 다시 계산**합니다.
재생하며 지나간 구간부터 타임라인이 사실에 맞게 교정됩니다.

## 4. 확인

단위 194개 · e2e 53개. 새로 붙인 것:

- 꼬리에 빈 패킷이 있어도 진짜 종료 시각을 찾는가 (2개)
- 짧게 잡혔던 구간을 고치면 빈 구간이 사라지는가 (3개)
- 막대를 파일 90% 지점으로 끌어도 그 파일에 머무는가 (1개)
