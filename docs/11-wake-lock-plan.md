# 열람 중 화면 잠김 방지 계획안

**결정이 필요한 항목은 D17~D19입니다.**

---

## 1. 무엇으로 하는가 — Screen Wake Lock API

브라우저에서 화면을 깨어 있게 하는 표준 방법은 이것 하나입니다.

```js
const sentinel = await navigator.wakeLock.request('screen');
```

할 수 있는 것과 없는 것을 먼저 분명히 해 둡니다.

| | |
|---|---|
| **막아 주는 것** | 가만히 두면 꺼지는 **화면 자동 꺼짐(시간 초과)** |
| 못 막는 것 | 전원 버튼으로 직접 잠그는 것 |
| 못 막는 것 | 다른 앱으로 넘어갔을 때 (그때는 잠금이 자동 해제됨) |

---

## 2. 가장 큰 걸림돌 — 보안 컨텍스트

이 API는 **보안 컨텍스트에서만** 동작합니다. 그런데 우리는 단일 HTML 파일을
폰에 내려받아 여는 방식이라 주소가 `https://`가 아닙니다.

공개 문서 중에는 **"HTTP와 `file://`에서는 예외를 던진다"** 고 적힌 것도 있습니다.
그래서 **직접 재 봤습니다.** 빌드된 단일 파일을 `file://`로 열고 확인한 결과:

```
file://   isSecureContext: true   wakeLock: ok (released=false)
http://   isSecureContext: true   wakeLock: ok (released=false)
```

`file://`은 보안 컨텍스트로 인정되고 **잠금 요청이 성공했습니다.**

### 방증이 하나 더 있습니다

지금 폰에서 **영상이 재생되고 있습니다.** WebCodecs(`VideoDecoder`)도
보안 컨텍스트를 요구합니다. 그게 되고 있다는 건 그 환경이 이미 보안
컨텍스트라는 뜻입니다.

> 다만 제 측정은 **이 컨테이너의 헤드리스 Chromium**입니다.
> 실제 안드로이드 Chrome이 파일을 `content://`로 열면 결과가 다를 수 있습니다.
> **그래서 대비책을 함께 준비하는 쪽을 권합니다(D18).**

---

## 3. 반드시 다시 잡아야 합니다

이걸 놓치면 "처음엔 되는데 잠깐 다른 앱 갔다 오면 안 되는" 증상이 됩니다.

> 문서가 비활성이 되면 **이미 얻은 잠금은 자동으로 풀립니다.**
> 다시 활성이 되면 `visibilitychange`를 듣고 **다시 요청해야** 합니다.

그래서 설계는 이렇습니다.

```
재생 화면 진입      → 잠금 요청
화면이 다시 보임     → 다시 요청 (자동 해제되었으므로)
재생 화면을 벗어남   → 놓아줌 (캘린더·빈 화면에서까지 켜 둘 이유가 없다)
```

사용자 제스처가 필요하다는 문서도 있습니다. 어차피 재생 화면에 들어오려면
날짜나 파일을 눌러야 하므로 **항상 제스처 뒤**입니다. 문제되지 않습니다.

---

## 4. 배터리

화면이 켜져 있는 것 자체가 폰에서 가장 큰 전력 소모입니다.
게다가 이 앱은 70MB 파일을 계속 읽고 두 채널을 디코딩합니다.

- 캘린더·빈 화면에서는 **반드시 놓아줍니다**
- 끌 수 있어야 합니다 (D19)
- 잠금이 걸려 있다는 걸 **사용자가 알 수 있어야** 합니다.
  모르는 사이에 배터리가 빠지면 안 됩니다

---

## 5. 결정 항목

### D17 — 언제 켤까요

| 안 | 내용 |
|---|---|
| **㉮ 재생 화면이 열려 있는 동안 계속** | 멈춰 놓고 화면을 들여다보거나 메모할 때도 안 꺼집니다. 요청하신 "열람 중"에 가장 가깝습니다 |
| ㉯ 재생 중에만 | 일반 영상 플레이어 방식. 일시정지하면 곧 꺼집니다 |
| ㉰ 사용자가 켤 때만 | 기본 꺼짐. 필요할 때만 켭니다 |

### D18 — 잠금 요청이 실패하면

실제 안드로이드에서 `file://`이나 `content://`가 막힐 가능성이 남아 있습니다.

| 안 | 내용 |
|---|---|
| **㉮ 숨은 무음 영상으로 대신** | 보이지 않는 1프레임짜리 영상을 무음 반복 재생합니다. 잠금 API가 없던 시절의 표준 우회법(NoSleep.js)입니다. 확실하지는 않고 배터리를 더 씁니다 |
| ㉯ 대비책 없이 안내만 | "이 환경에서는 화면 잠김을 막을 수 없습니다"를 한 번 띄우고 맙니다. 군더더기가 없습니다 |

㉮의 위험: 우리 앱은 이미 Web Audio로 소리를 내고 WebCodecs로 영상을
디코딩합니다. 숨은 영상이 오디오 초점이나 디코더와 부딪힐 수 있어
**실기기 확인이 필요합니다.**

### D19 — 어디에 표시/조작할까요

상단바(`‹날짜 ★2 폴더 파일`)와 컨트롤 줄(`⏮ ⟲10 ▶ 10⟳ ⏭ 1x 🔊 ☆`)이
이미 꽉 차 있어서 자리가 마땅치 않습니다.

| 안 | 내용 |
|---|---|
| **㉮ 파일 정보 줄에 작은 칩** | `구간 15/22 · 출처 data/…` 줄 끝에 `🔆 화면 켜둠` 칩. 누르면 꺼집니다. 자리를 새로 만들지 않아도 됩니다 |
| ㉯ 컨트롤 줄에 아이콘 버튼 | 눈에 가장 잘 띕니다. 대신 폰에서 버튼이 하나 더 늘어 좁아집니다 |
| ㉰ 표시 없이 자동 | 가장 단순하지만 **모르는 사이에 배터리가 빠집니다.** 권하지 않습니다 |

---

## 6. 제 권고

**D17은 ㉮, D18은 ㉮, D19는 ㉮입니다.**

- 감사용으로 한 장면을 멈춰 놓고 들여다보는 일이 잦으므로
  "재생 중에만"으로는 요청을 못 채웁니다
- `file://`에서 된다는 건 확인했지만 **제 환경에서만** 확인한 것이라,
  실패했을 때 조용히 아무것도 안 하는 것보다 우회법이라도 있는 편이 낫습니다.
  대신 **잠금 API가 성공하면 우회법은 쓰지 않습니다** (배터리·충돌 회피)
- 켜져 있다는 사실은 반드시 보여야 하고, 한 번 눌러 끌 수 있어야 합니다

작업량은 크지 않습니다. 핵심 로직 약 80줄 + 화면 20줄 + 테스트입니다.

---

## 7. 구현 결과 (D17 ㉮ · D18 ㉮ · D19 ㉮)

- 재생 화면이 열려 있는 동안 잠금을 겁니다. 캘린더·빈 화면으로 나가면 놓습니다
- `visibilitychange`에서 **다시 잡습니다.** 자동 해제되므로 이게 없으면
  앱 전환 뒤에 안 걸립니다
- 표준이 막히면 **보이지 않는 1px 영상**으로 대신합니다. 다만 파일을
  base64로 박는 대신 **캔버스 스트림**을 씁니다 — 단일 HTML에 영상을
  넣지 않아도 되고, 소리 트랙이 없어 우리 Web Audio와 오디오 초점을
  다투지 않습니다. 표준이 성공하면 우회법은 쓰지 않습니다
- 파일 정보 줄 끝에 `🔆 화면 켜둠` 칩. 누르면 꺼지고, 한 번 끄면 그 세션
  동안은 자동으로 켜지 않습니다
- 못 막는 환경이면 칩이 `화면 잠김 못 막음`으로 비활성됩니다
