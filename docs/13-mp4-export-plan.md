# 내보내기를 "분석 보조 자료"로 다시 세우는 계획안

**결정이 필요한 항목은 D20~D23입니다.**

---

## 1. 짚어 주신 전제에 동의합니다

```
원본 JDR은 건드리지 않는다  →  내보낸 파일은 원본이 아니라 파생물
파생물은 분석을 돕는 수단   →  바이트를 원본과 맞출 이유가 없다
```

지금까지 저는 이 전제를 반쯤만 적용하고 있었습니다. 그래서 영상을
**재인코딩하지 않고 Annex-B 스트림을 그대로 잘라 붙이는** 방식만 썼고,
그 결과 나오는 게 `.h264` + `.wav`입니다.

**이건 폰에서도 PC에서도 그냥 안 열립니다.** 감사 보고서에 붙일 수도,
남에게 보낼 수도 없습니다. 전제를 끝까지 적용하면 **MP4**로 내보낼 수 있습니다.

---

## 2. 무엇이 가능해지는가

| | 지금 | 전제를 적용하면 |
|---|---|---|
| 영상 | `.h264` (전용 도구만 열림) | **MP4** (어디서나 열림) |
| 음성 | `.wav` 별도 파일 | 영상 안에 함께 |
| 전방·후방 | 파일 두 개 | 두 개 / 또는 **한 화면 합성** |
| 시각 | 파일명에만 | 파일 안 메타데이터로도 |

### 영상은 여전히 재인코딩하지 않아도 됩니다

MP4로 바꾸는 데 화질 손실이 필요 없습니다. **담는 그릇만 바꾸는 것**
(리먹스)이라 픽셀은 원본 그대로입니다. 할 일은 두 가지뿐입니다.

- Annex-B 시작코드(`00 00 00 01`)를 **길이 접두사**로 바꾸기
- 키프레임의 SPS·PPS를 뽑아 **avcC 상자**로 넣기

둘 다 이미 있는 코드로 됩니다 (`core/nal.ts`의 `findNalUnits`·`parseSps`).
빠르고 배터리도 거의 안 씁니다.

### 음성은 손을 대야 합니다 — 여기가 유일한 위험

MP4에 두루 통하는 음성은 **AAC**입니다. 우리 원본은 **8kHz 모노 PCM**인데,
크롬의 AAC 인코더가 8kHz를 받아 줄지 확신할 수 없습니다.

**이 컨테이너에서는 확인이 불가능했습니다.** 여기 크롬에는 독점 코덱이
빠져 있어 H.264·AAC 인코더 자체가 없습니다 (직접 확인):

```
mp4a.40.2 @ 8000/16000/44100 → 전부 no      (독점 코덱 없음)
avc1.*                       → 전부 no
vp8 / vp9 / opus             → ok
```

폰에서는 H.264가 재생되니 코덱은 있습니다만, **인코딩은 실기기에서
확인해야 합니다.**

→ 그래서 **48kHz로 올려서 AAC로 넣는** 쪽을 권합니다. 낮은 표본율을
받아 주느냐는 문제를 아예 피합니다. 없던 소리가 생기지는 않지만
파일은 어디서나 열립니다.
**손대지 않은 8kHz 원본이 필요하면 지금의 WAV 내보내기가 그대로 남습니다.**

## 3. 무엇으로 만들까

직접 만들어 볼까도 했지만(이 프로젝트는 SHA-256·VAD·시간 신축을 다 직접
썼습니다), MP4는 **틀리면 파일이 아예 안 열리는** 형식이라 라이브러리를
권합니다. 4GB 넘는 파일(`co64`), 청크 오프셋, 가변 프레임 간격처럼
조용히 틀리기 쉬운 곳이 많습니다.

**단일 HTML 파일에 함께 묶이므로 실행 시점에 내려받는 건 없습니다.**
(ONNX 런타임과 달리 오프라인·`file://` 성질을 깨지 않습니다.)

실제로 넣고 빌드해서 크기를 재 봤습니다.

| | 단일 파일 크기 | 늘어남 |
|---|---|---|
| 지금 | 406,248 | — |
| **mp4-muxer** | 438,074 | **+31.8 KB** |
| **mediabunny** | 524,436 | **+118 KB** (최소치) |
| 직접 구현 | 406KB + 약 400줄 | 0 KB |

mp4-muxer는 가볍지만 **"Mediabunny로 옮기라"며 deprecated**로 표시돼
있습니다. mediabunny는 같은 개발자의 후속작이고 유지보수 중입니다.

---

## 4. 전방·후방을 한 화면에?

이것도 전제를 적용하면 가능해집니다. 다만 **합성은 재인코딩입니다.**

```
전방 디코딩 + 후방 디코딩 → 캔버스에 나란히 → 다시 인코딩
```

폰에서 5분짜리를 만드는 데 1~3분, 발열과 배터리도 상당합니다.
반면 리먹스는 읽고 쓰기만 하므로 거의 즉시입니다.

감사 보고서에 "한 장면에 앞뒤가 같이" 붙는 건 분명 쓸모가 있지만,
**기본은 각각 두 개, 합성은 고를 수 있게** 하는 편이 낫다고 봅니다.

> 합성본에는 **"JDR Viewer가 만든 화면"** 표시를 구석에 넣겠습니다.
> 전방 영상에는 기기가 새긴 시각(`2026/09/12 11:44:58PM …`)이 이미 있는데,
> 우리가 그린 글자와 기기가 새긴 글자가 구별되지 않으면 안 됩니다.

---

## 5. 해시 대신 무엇으로 원본과 잇는가

"바이트를 맞출 필요가 없다"는 데 동의하지만, **어느 원본에서 나온
파생물인지는 남아야** 감사에서 쓸 수 있습니다. 바이트로 못 이으면
**글로 이어야** 합니다.

MP4 안에 메타데이터로 넣을 수 있습니다 (파일 하나로 끝나고, 옮겨도 따라갑니다).

```
제목   260909_075713-080213 전방
설명   JDR Viewer 내보내기 (파생물 · 원본 아님)
       원본: data/00000440.jdr ~ data/00000445.jdr (6개)
       구간: 2026-09-09 07:57:13 ~ 08:02:13
       영상: 재인코딩 없음 / 음성: 8kHz PCM → 48kHz AAC
```

원본 SHA-256까지 넣으려면 원본 6개를 통째로 읽어야 합니다
(420MB, 약 7초). **선택 항목**으로 두겠습니다.

## 6. 결정 항목

### D20 — 내보내기 형식
㉮ **MP4로 바꾸고 raw는 없앤다** (영상은 재인코딩 없음) /
㉯ MP4를 기본으로 하되 raw도 남긴다 /
㉰ 지금처럼 raw만

### D21 — 전방·후방
㉮ **각각 MP4 두 개** (빠름, 기본) /
㉯ 한 화면 합성 하나만 (재인코딩, 느림) /
㉰ 둘 다 고를 수 있게

### D22 — 무엇으로 만들까
㉮ **mediabunny** (+118KB, 유지보수 중) /
㉯ mp4-muxer (+32KB, deprecated) /
㉰ 직접 구현 (0KB, 틀리면 파일이 안 열림)

### D23 — 원본과 잇는 기록
㉮ **MP4 메타데이터로** (파일 하나로 끝남) /
㉯ 별도 사이드카 파일로 /
㉰ 둘 다 /
㉱ 안 넣음

## 7. 제 권고

**D20 ㉯ · D21 ㉰ · D22 ㉮ · D23 ㉮입니다.**

- **D20을 ㉯로**: MP4가 기본이어야 하지만, raw는 남겨 두겠습니다.
  재인코딩 없는 비트스트림이 필요한 상황(다른 포렌식 도구에 넣기)이
  생길 수 있는데, 이미 있는 코드라 남기는 비용이 0입니다
- **D21을 ㉰로**: 기본은 두 개(빠름), 합성은 눌러서. 폰에서 몇 분 걸리는
  일을 기본으로 두면 안 됩니다
- **D22를 mediabunny로**: +86KB를 더 쓰는 대신 deprecated를 피합니다.
  단일 파일이 406KB → 약 525KB인데, 파일 하나가 70MB인 걸 다루는
  앱에서 이 정도는 문제가 아닙니다
- **D23을 메타데이터로**: 사이드카는 잃어버리기 쉽습니다.
  SHA-256은 기본 꺼둠(비쌈), 필요하면 켜기

### 진행하면 이렇게 검증하겠습니다

만든 MP4를 **브라우저로 다시 열어 디코딩되는지** e2e에서 확인합니다
(VP8로라도 — 이 환경에는 H.264 인코더가 없지만 **리먹스는 인코더가
필요 없으므로** 실제 H.264 리먹스 경로도 검증할 수 있습니다).
다만 **AAC 인코딩만은 실기기 확인이 필요합니다.**
