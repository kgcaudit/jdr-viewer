# JDR 파일 포맷 사양 (역분석 결과 정리)

> 출처: 사용자가 제공한 `JDR_Extractor_Code_Package.zip`
> (`reference/jdr_extractor_tool/jdr_extractor.py`)을 정독하여 정리한 것입니다.
> 제조사(IROAD) 공식 사양이 아니며, 샘플 `00000000.jdr` 1개로 검증된 추정 사양입니다.
> 안드로이드 앱의 파서는 이 문서를 구현 기준으로 삼습니다.

---

## 1. 전체 구조

JDR 파일은 **JEB 블록이 1개 이상 연속**된 구조입니다.

```
┌────────────────────────────┐
│ JEB 헤더 (0x200 = 512 byte)│  ← magic "1BEJ"
├────────────────────────────┤
│ 패킷 0  (헤더 28B + 페이로드)│
│ 패킷 1                      │
│ ...                        │
│ 패킷 N-1                    │
├────────────────────────────┤
│ 인덱스 테이블 (12B × N)      │  ← 헤더 +0xB8 이 가리키는 위치
└────────────────────────────┘
   (파일 끝까지 위 블록이 반복될 수 있음)
```

블록의 시작 위치는 파일 전체에서 magic을 **탐색(scan)** 해서 찾습니다.
단순 magic 일치만으로는 오탐이 발생하므로 아래 검증을 모두 통과해야 유효 블록입니다.

## 2. JEB 헤더 (512 bytes)

magic `JEB1`(DWORD 0x4A454231)은 리틀엔디안이므로 **디스크상 바이트는 `31 42 45 4A` = `"1BEJ"`** 입니다.
파일에서 검색할 바이트열은 `"1BEJ"` 입니다.

| 오프셋 | 크기 | 타입 | 의미 |
|---|---|---|---|
| +0x00 | 4 | bytes | magic `"1BEJ"` |
| +0x04 | 4 | u32 LE | **패킷 개수 N** |
| +0x08 | 4 | u32 LE | 채널 0 영상 패킷 수 |
| +0x0C | 4 | u32 LE | 채널 1 영상 패킷 수 |
| +0x48 | 4 | u32 LE | 오디오 패킷 수 |
| +0x88 | 4 | u32 LE | GPS 패킷 수 |
| +0x8C | 4 | u32 LE | G센서 패킷 수 |
| +0x94 | 16 | SYSTEMTIME | 블록 시작 시각 |
| +0xA4 | 16 | SYSTEMTIME | 블록 종료 시각 |
| +0xB8 | 4 | u32 LE | **인덱스 테이블 오프셋** |
| +0xF8 | 0x48 | ASCII(NUL 종단) | GPS 힌트 문자열 |
| +0x1FC | 4 | u32 LE | **헤더 크기 sentinel = 0x200** |

### 유효 블록 판정 조건 (오탐 제거)

1. `u32(+0x1FC) == 0x200`
2. `0 < N < 10,000,000`
3. `0 <= indexOffset < fileSize`
4. `indexOffset + N * 12 <= fileSize`
5. 헤더 전체(512B)가 파일 범위 안에 있을 것

## 3. 패킷 헤더 (28 bytes)

패킷은 헤더 직후(`블록시작 + 0x200`)부터 **빈틈없이 연속**됩니다.
다음 패킷 위치 = `현재 패킷 페이로드 시작 + payloadSize`.

| 오프셋 | 크기 | 타입 | 의미 |
|---|---|---|---|
| +0x00 | 4 | ASCII | 태그 (예: `00VI`) |
| +0x04 | 4 | u32 LE | 페이로드 크기 |
| +0x08 | 4 | u32 LE | aux / 시퀀스 번호 |
| +0x0C | 16 | SYSTEMTIME | 패킷 타임스탬프 |
| +0x1C | - | - | 페이로드 시작 |

### Windows SYSTEMTIME (16 bytes, u16 × 8, LE)

`year, month, dayOfWeek, day, hour, minute, second, milliseconds`
→ `dayOfWeek`(3번째 필드)는 버립니다. 밀리초까지 유효합니다.

### 태그 체계

태그는 `[채널2자리][종류2자리]` 구조입니다.

| 태그 | 의미 |
|---|---|
| `00VI` | 채널0(전방) H.264 **I-프레임** |
| `00VP` | 채널0(전방) H.264 **P-프레임** |
| `01VI` | 채널1(후방) H.264 I-프레임 |
| `01VP` | 채널1(후방) H.264 P-프레임 |
| `xxAD` | PCM 오디오 |
| `xxGP` | GPS |
| `xxSE` | G센서 |

판별 규칙(원본 코드 기준):
- 영상: `tag[0..1] == "00"/"01"` **그리고** `tag[2] == 'V'`
- 그 외: `tag[2..3]` 이 `"AD"`, `"GP"`, `"SE"` 인지로 판별 (채널 자리는 무시)

## 4. 인덱스 테이블 (엔트리 12 bytes)

`indexOffset`부터 N개가 연속됩니다.

| 오프셋 | 크기 | 의미 |
|---|---|---|
| +0x00 | 4 | 태그 |
| +0x04 | 4 | 페이로드 크기 |
| +0x08 | 4 | **패킷 시작 오프셋(파일 절대 위치)** |

> **앱에서 중요**: 이 테이블은 순차 파싱 없이 곧바로 랜덤 액세스가 가능한
> **시크(seek) 인덱스**입니다. `00VI`(I-프레임) 엔트리만 골라내면
> 그것이 곧 영상 탐색 키프레임 목록이 됩니다. (→ `docs/01-android-knowledge.md` 5장)

원본 코드는 순차 파싱 결과와 인덱스를 대조해 불일치 개수를 세고,
`--strict-index` 옵션에서는 불일치 시 중단합니다. 앱도 동일한
**무결성 검증(mismatch count)** 을 유지해야 합니다.

## 5. 페이로드 포맷

### 5.1 영상 (VI / VP)

- H.264 **Annex-B** (start code `00 00 01` 또는 `00 00 00 01` 포함)
- 패킷 페이로드를 **순서대로 그대로 이어붙이면** 재생 가능한 elementary stream이 됨
- 샘플: 1280×720, 채널당 약 30 fps
- fps는 고정 메타데이터가 아니라 **타임스탬프로 추정**해야 함
  (샘플이 33ms/34ms를 번갈아 쓰므로 중앙값은 30.303fps로 틀림 →
  `(프레임수-1) / (마지막시각 - 첫시각)` 장구간 평균 사용, 이후 표준 fps로 스냅)

### 5.2 오디오 (AD)

- PCM **signed 16-bit little-endian**, **8,000 Hz**, **모노**
- 패킷 페이로드를 순서대로 이어붙이면 그대로 PCM 스트림

### 5.3 GPS (GP) — 페이로드 96바이트 이상

| 오프셋 | 타입 | 의미 |
|---|---|---|
| +0x00 | i32 × 10 | `[0]` 미상, `[1]`년 `[2]`월 `[3]`일 `[4]`시 `[5]`분 `[6]`초, `[7..9]` 미상 |
| +0x28 | f64 × 7 | pdop, hdop, vdop, **위도**, **경도**, 고도(m), 속도(km/h) |

위/경도는 **NMEA `ddmm.mmmm` 형식**이므로 십진 도(degree)로 변환 필요:

```
deg = trunc(|v| / 100)
min = |v| - deg * 100
결과 = sign(v) * (deg + min / 60)
```

### 5.4 G센서 (SE) — 페이로드 12바이트 이상

- `i32 × 3` = X, Y, Z **raw**
- 샘플에서 정지 시 Z ≈ 1024 → **1024 raw ≈ 1g** 로 추정
- `g = raw / 1024.0` (추정치이므로 앱 UI에도 "추정" 표기 필요)

## 6. 무결성 / 증거 취급

- 원본 JDR은 **읽기 전용**으로만 열기 (원본 무수정)
- 입력 파일 **SHA-256**을 요약에 기록
- 추출된 MP4/CSV는 **파생물**이며, 원본성 판단 기준은 원본 JDR + 해시
- GPS/G센서 세부 필드는 역공학 추정치 → 법적·감정 용도로 쓸 경우
  제조사 사양 또는 추가 샘플 검증 병행 필요

## 7. 미확정 / 추가 확인 필요 항목

| 항목 | 현재 상태 |
|---|---|
| 헤더 내 다른 필드 (0x10~0x47, 0x4C~0x87, 0x90, 0xB0 등) | 미상 |
| GPS 구조체 i32 `[0]`, `[7..9]` | 미상 |
| 패킷 헤더 `aux` 필드의 정확한 의미 | 시퀀스/샘플 인덱스로 추정 |
| G센서 스케일(1024 = 1g) | 샘플 1개 기반 추정 |
| 다른 기종/펌웨어의 JDR 변형 | 미검증 — 앱은 **파싱 실패를 우아하게 처리**해야 함 |
| 오디오 태그의 채널 자리(`xx`) 의미 | 미상 (현재는 무시) |
| 암호화/스크램블 여부 | 샘플에는 없음 |
