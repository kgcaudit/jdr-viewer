## 2. 검증하지 **못한** 것

### H.264 디코딩 그 자체

이 개발 컨테이너의 Chromium은 **독점 코덱이 빠진 오픈소스 빌드**입니다.
직접 확인한 결과:

```
dec:avc1.42001f  false      dec:vp8   true
enc:avc1.42001f  false      enc:vp8   true
```

그래서 E2E는 **VP8로 만든 합성 JDR**로 돌렸습니다.
이 경로는 H.264와 **완전히 동일한 코드**를 지납니다 —
`VideoDecoder` 생성·설정, JDR 태그(`00VI`/`00VP`) → `EncodedVideoChunk`의 `key`/`delta`,
패킷 타임스탬프 → `timestamp`, 캔버스 렌더, I-프레임 인덱스 시크.

**H.264 고유 부분만 다른 방식으로 검증했습니다.**

| H.264 고유 요소 | 검증 방법 |
|---|---|
| SPS 파싱 (해상도·코덱 문자열) | 실제 1080p SPS 유닛 테스트 ✅ |
| Annex-B NAL 스캔 | 유닛 테스트 ✅ |
| 키프레임에 SPS/PPS 붙이기 | 유닛 테스트 ✅ |
| **실제 H.264 비트스트림 디코딩** | ❌ **미검증** — H.264 지원 브라우저 필요 |

→ **일반 Chrome이나 Safari에서 실제 JDR 파일로 한 번 확인하면 끝납니다.**

### 실제 JDR 파일

샘플 `.jdr`이 없어 **합성 파일로만** 검증했습니다. 실제 파일에서 확인할 것:

1. **`00VI` 패킷에 SPS/PPS가 들어있는가** — 앱이 이 결과를 요약 패널에
   "H.264 비트스트림 점검"으로 직접 보여줍니다. 없으면 주변 패킷에서 찾아
   자동으로 앞에 붙입니다.
2. GPS 구조체의 미상 필드, 속도 단위
3. 오디오 패킷이 실제로 끊기는 구간(주차모드)에서 무음 채우기가 맞는지
4. 대용량(수백 MB~GB) 파일의 파싱 시간과 메모리

### 지도 타일

컨테이너에서 외부 네트워크가 막혀 OSM 타일이 회색으로 나옵니다.
경로 폴리라인과 마커는 정상 렌더되므로 실제 브라우저에서는 배경까지 나옵니다.

## 3. 개발 중 찾아 고친 버그

프로토타입을 돌려보며 실제로 잡은 것들입니다.

| 버그 | 증상 | 원인 |
|---|---|---|
| **모든 프레임이 버려짐** | 영상이 전혀 안 나옴 | 디코더 출력 콜백이 생성 시점의 `generation`을 클로저에 가둬, `seek()` 한 번이면 영구히 낡은 값이 됨. `reset()`이 이전 콜백을 취소해 주므로 가드 자체가 불필요 |
| **재생 버튼이 먹히지 않음** | 간헐적으로 눌러도 무반응 | 파싱 직후 UI는 떴지만 `player`가 아직 없어 클릭이 조용히 무시됨 → 준비 전까지 컨트롤 비활성화 |
| **재생이 되감김** | 빠르게 재생을 누르면 0초로 돌아가 멈춤 | `init()` 끝의 `seek(0)`이 그 사이의 사용자 조작을 덮어씀 |
| **SHA-256 값이 두 번째 호출부터 틀림** | 해시 불일치 | 패딩 압축이 내부 상태를 바꾸는데 결과를 캐시하지 않음 |
| **잘린 파일을 통째로 거부** | "유효한 JEB1 블록 없음" | 인덱스 테이블이 파일 밖을 가리키면 헤더를 버림. 녹화 중 전원이 끊긴 파일이 그럼 → 블록은 살리고 "인덱스 없음"으로 표시 |
| **음성 실패가 영상까지 막음** | 오디오 장치 없으면 재생 불가 | `play()`에서 `audio.start()` 예외가 전파됨 |
| **차트 겹침** | 범례가 다음 차트 제목을 덮음 | 컨테이너 고정 높이가 uPlot 실제 높이보다 작음 |
