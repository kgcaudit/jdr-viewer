# 실기기 인덱스 검토 (826개 · 45.1GB · 2026-09-03 ~ 09-12)

추론으로 쫓던 것들을 **실제 카드의 인덱스 파일**로 확인했다. v6 인덱스,
826행. 여기서 확정된 것과 새로 나온 결함을 적는다.

## 1. "826개 읽음 / 파일 660개" — 숫자는 맞다. 설명이 없는 게 문제다

```
data   660개  오류 0개
event  166개  오류 166개  (전부)
```

826 − 166 = 660. 계산은 맞다. 그런데 **166개가 어디로 갔는지 화면에 한 줄도
없었다.** 45GB 중 11.6GB, 전체의 20%가 소리 없이 빠졌다. 감사 자료에서
증거가 말없이 사라지면 그 도구는 못 믿는다.

→ 캘린더 "불러온 방식"에 몇 개가 왜 빠졌는지 적는다.

## 2. event 166개는 고장이 아니라 **아직 녹화되지 않은 빈 파일**이다

지금까지 `JEB1 블록을 찾지 못했습니다 (JDR이 아니거나 지원하지 않는 변형)`
이라고 말하고 있었다. **틀린 진단이다.** 인덱스가 증거를 준다.

| | event | data |
| --- | --- | --- |
| 개수 | 166 | 660 |
| 크기 | 전부 정확히 70.0 MB | 전부 정확히 70.0 MB |
| 수정시각 | **164개가 전부 `2024-09-22 22:13:10`** | 2026-09-02 ~ 09-12 |
| 파일 번호 | 0~165 빠짐 없음 | 0~659 빠짐 없음 |

164개의 수정시각이 **초 단위까지 똑같고**, 녹화보다 2년 앞선다. 이건 녹화된
파일이 아니라 **카드를 포맷할 때 기기가 미리 잡아 둔 자리**다. 충격 이벤트가
없었으니 아직 아무것도 안 쓴 것이다.

→ 0으로만 차 있으면 `빈 파일`로 가른다. "읽지 못한 파일"과 섞어 세지 않는다.
앞머리 4MB는 어차피 읽으므로 **읽기를 한 번도 늘리지 않고** 판별한다.

## 3. 영상 파일 누락은 **0건**이다

data 파일 번호가 **0~659, 하나도 안 빠졌다.** 앞서 빈 구간의 원인으로
의심했던 "루프 녹화 덮어쓰기로 파일이 없어짐"은 이 카드에서는 해당이 없다.
빈 구간은 전부 주차(시동 꺼짐)다.

## 4. 5시간짜리 구간 문제는 고쳐졌다 — 실데이터로 확인

보고된 그 파일이다.

```
00000223.jdr  10:25:04 → 10:25:54   49.4s  30.0fps
00000224.jdr  10:25:54 → 10:26:52   57.8s  30.0fps   ← 5시간 35분이었다
00000225.jdr  16:01:39 → 16:02:26   47.5s  30.0fps
```

`endEstimated=1` — 담긴 프레임이 받쳐 주지 못하는 길이라 방어선이 잡아냈다.
9/5가 **운행 2건(09:56~10:26 / 16:01~16:35)** 으로 갈라진 것도 화면으로 확인됐다.

전체 660개의 암시 프레임률: **p10 29.98 / p50 30.00 / p90 30.02.** 기기는
아주 일정하게 30fps로 찍는다. 길이가 부풀어 있으면 이 값이 무너지므로
좋은 검산 기준이다.

## 5. 새 결함 — **파일 하나 안에서 녹화가 끊긴다**

30fps에서 벗어난 파일이 딱 하나 남았다.

```
00000437.jdr  22:54:33 → 22:55:48     74.9s  fr=2249  30.01fps  blk=2
00000438.jdr  22:55:48 → 23:16:20   1232.1s  fr=2584   2.10fps  blk=6   ← 이것
00000439.jdr  23:16:20 → 23:17:50     89.7s  fr=2693  30.01fps  blk=2
```

앞뒤는 30fps인데 이것만 2.1fps다. 2584프레임은 30fps로 **86초**어치다.
나머지 **약 20분은 녹화가 없다.**

원인은 지금까지 고쳐 온 것과 같은 뿌리지만 **자리가 다르다.** 기기는 미리
잡아 둔 파일 하나에 **이어서** 쓴다. 22:55:48에 주차하고 23:16:20에 시동을
걸면, 같은 파일 안에 20분짜리 구멍이 생긴다. 파일 사이가 아니라 **파일
안**이라 지금까지의 방어선이 전부 비껴갔다.

`durationExceedsContent`(패킷 하나에 1초)도 못 막았다 — 이 파일은 패킷이
7570개라 7570초까지 허용된다. 길이만 보는 방어선의 한계다.

→ 블록 헤더마다 시간 범위가 적혀 있으므로, **블록 사이가 10초 넘게 비면
"파일 안 공백"으로 센다.** 프로브는 이미 모든 블록 헤더를 읽으므로 추가
읽기가 없다. 그만큼을 "실제 영상"에서 빼고, 요약·구간 탭에 밝힌다.

## 6. 잡아낸 내 오류 — 커버리지 경고가 늑대를 부를 뻔했다

```
블록이 덮은 비율:  p50 = 97.9%,  98% 미만 = 660개 중 628개
```

전날 넣은 "파일 읽힌 정도"는 98% 미만을 경고로 띄운다. 그대로 뒀으면
**멀쩡한 파일 628개가 경고로 떴을 것이다.**

원인은 단순하다. 파일은 70MB로 **미리 잡혀 있고** 녹화는 그보다 일찍 끝난다.
남은 2.1%는 못 읽은 게 아니라 **안 쓴 자리**다. 늑대가 왔다고 매번 외치면
진짜일 때 아무도 안 본다.

→ 꼬리가 0으로 차 있으면 "다 읽은 것"으로 센다. 다만 **끝을 반드시 표본에
넣는다** — 패딩 뒤 맨 끝에 블록이 붙은 파일을 놓치면 정반대 실수가 된다.

## 남은 것

- `blank` 판별은 앞 4MB 전수 + 그 뒤 표본이다. 파일 한복판에만 데이터가
  있는 변종은 놓칠 수 있다. 실기기에서는 못 봤다.
- 파일 안 공백은 **세고 알리기만** 한다. 띠(스트립)는 그 파일을 아직 한 덩어리로
  칠한다. 제대로 그리려면 구간을 쪼개야 하는데, 재생·탐색의 기준 시각이 함께
  바뀌어야 해서 따로 다룬다.
