# 폴더 열기 + 시간축 병합 재생 — 계획안

> 요청: ① 파일 열기 외에 **폴더 열기** ② 폴더를 열면 파일 단위가 아니라
> **같은 시간 영역대로 병합 재생**
>
> 이 문서는 착수 전 의사결정을 위한 것입니다. 성능 수치는 이 환경에서 실측한 값입니다.
>
> **결정 완료 (구현됨)** — D1 연속 이어붙이기 · D2 벽시계 축 + 갭 건너뛰기 ·
> D3 짧은 끊김 허용 + 미리읽기 · D4 열자마자 백그라운드 스캔.
> 실제 기기 폴더 구조를 확인한 뒤 바뀐 부분은 11장에 정리했습니다.

---

## 1. 핵심 발견 — 이게 계획 전체를 결정합니다

폴더 안의 파일을 **전부 파싱하면 안 됩니다.** 대신 **JEB 헤더 512바이트만** 읽으면
각 파일의 시간 범위·패킷 수·채널 구성을 알 수 있습니다.

실측 (12개 파일, 합계 145MB):

| 방식 | 소요 | 파일당 |
|---|---|---|
| **헤더 512B만 읽기** | **2ms** | **0.2ms** |
| 전체 파싱 | 4,303ms | 359ms |

**2,152배 차이**입니다. 이 덕분에:

| 폴더 크기 | 헤더 인덱싱 | (참고) 전체 파싱 |
|---|---|---|
| 12개 | 2ms | 4.3초 |
| 100개 | ~20ms | ~36초 |
| 1,000개 | ~0.2초 | ~6분 |

→ **폴더를 열면 1초 안에 전체 타임라인이 뜨고**, 실제 파싱은 재생하는 구간만
필요할 때 합니다.

### 헤더에서 뽑는 정보 (사양 문서 2장)

| 오프셋 | 값 |
|---|---|
| +0x04 | 패킷 수 |
| +0x08 / +0x0C | CH0 / CH1 영상 패킷 수 |
| +0x88 / +0x8C | GPS / G센서 패킷 수 |
| **+0x94 / +0xA4** | **블록 시작 / 종료 시각** ← 타임라인의 핵심 |

**확인 필요**: 실제 IROAD 파일에서 이 시각 필드가 채워져 있는지.
비어 있으면 **폴백**으로 첫 패킷 헤더(+0x200)와 인덱스 테이블 마지막 항목을 읽어
실제 범위를 구합니다 — 읽기 3번, 여전히 전체 파싱의 1/1000 비용입니다.

## 2. 폴더 열기 — 어떻게

| 방식 | 지원 | 판단 |
|---|---|---|
| **`<input webkitdirectory>`** | Chrome 7+, Edge, **Firefox 50+, Safari 11.1+(macOS) / 18.4+(iOS)** | ✅ **기본** |
| 폴더 드래그 앤 드롭 (`webkitGetAsEntry`) | 데스크톱 전 브라우저 | ✅ 같이 지원 |
| `showDirectoryPicker()` | **Chromium 전용** (Firefox·Safari 미지원) | 선택적 — 재방문 시 권한 유지가 장점 |

→ `webkitdirectory`를 기본으로 하고 드래그 앤 드롭을 함께 지원합니다.
Chromium에서만 `showDirectoryPicker()`를 추가로 제공할지는 **결정 필요**(3장 D4).

하위 폴더도 한 번에 들어오므로 IROAD의 `Normal` / `Event` / `Parking` 같은
구조를 그대로 읽을 수 있습니다. `webkitRelativePath`로 어느 폴더 소속인지 구분합니다.

## 3. "병합"의 두 가지 의미 — 결정이 필요합니다

요청하신 "동일 시간 영역대 병합"은 두 가지로 읽힙니다. 설계가 크게 갈립니다.

### (A) 연속 병합 — 시간순으로 이어 붙이기

```
파일1 [09:00~09:10]  파일2 [09:10~09:20]  파일3 [09:20~09:30]
└──────────────── 하나의 타임라인 ────────────────┘
        스크럽·재생이 파일 경계를 넘어 계속됨
```

파일이 시간 단위로 쪼개져 있을 때, 경계를 의식하지 않고 쭉 보는 것.
**대부분의 블랙박스 뷰어가 하는 일**이고, 요청의 핵심으로 보입니다.

### (B) 동시 병합 — 같은 시각의 여러 소스를 함께

```
Normal  [09:00 ─────────────── 09:30]
Event        [09:12~09:14]              ← 같은 시각, 다른 파일
Parking                    [09:25~09:28]
              ↓
        같은 시각을 여러 트랙으로 표시, 원하는 소스 선택
```

사고 순간이 `Event` 폴더에 따로 저장되어 `Normal`과 **겹치는** 경우,
또는 전방/후방이 별도 파일로 나뉜 경우입니다.

> **(A)와 (B)는 배타적이지 않습니다.** (A)를 먼저 만들고 (B)를 얹는 것이 자연스럽습니다.
> 다만 (B)가 필요 없다면 트랙 모델을 단순화해 작업량이 줄어듭니다.

## 4. 타임라인 축 — 두 번째 결정

세그먼트 사이에 **빈 구간(갭)** 이 생깁니다 (주차 중, 전원 차단, 녹화 안 된 시간).

### 벽시계 축 (실시간)

```
09:00 ──[영상]──09:10  (빈 구간 09:10~09:25)  09:25──[영상]──09:30
       축의 간격 = 실제 흐른 시간
```
- ✅ **증거·감사 용도에 정확** — "몇 시 몇 분에 무엇이"가 축 위에서 바로 보임
- ✅ 빈 구간 자체가 정보 (녹화 공백)
- ❌ 빈 구간이 길면 타임라인 대부분이 비어 보임

### 연속 축 (갭 제거)

```
09:00 ──[영상]──09:10 | 09:25──[영상]──09:30
       빈 구간을 접어서 영상만 이어 붙임
```
- ✅ 스크럽이 촘촘하고 보기 편함
- ❌ 축 위치와 실제 시각이 달라짐

**권장**: **벽시계 축을 기본**으로 하고, 빈 구간을 타임라인에 회색으로 표시하며,
재생 중 빈 구간은 **자동으로 건너뛰기**(옵션). 두 방식의 장점을 대부분 가져옵니다.

## 5. 파일 경계 처리 — 세 번째 결정

세그먼트가 바뀔 때 디코더를 다시 설정해야 합니다 (파일마다 SPS가 다를 수 있음).

| 방식 | 경계에서 | 구현 난이도 |
|---|---|---|
| **단일 디코더 재설정** | 수백 ms 정도 멈칫할 수 있음 | 낮음 |
| **디코더 2개 더블 버퍼링** | 무단절 | 높음 — 채널당 2개 × 2채널 = 디코더 4개. 저가 기기에서 동시 인스턴스 한계에 걸릴 수 있음 |

**권장**: 단일 디코더 + **미리 읽기**(다음 세그먼트를 2초 전에 파싱·키프레임 준비)로 시작.
실제로 거슬릴 만큼 끊기면 그때 더블 버퍼링을 검토합니다.

## 6. 메모리 — 전부 올리면 터집니다

패킷 테이블은 패킷당 약 24바이트입니다(SoA 구조).

| 파일 | 패킷 수(추정) | 패킷 테이블 |
|---|---|---|
| 1시간 1개 | ~40만 | ~10MB |
| 24개 전부 | ~960만 | **~240MB** ← 위험 |

**해결**: 세그먼트 인덱스(파일당 100바이트 수준)만 전부 들고 있고,
**패킷 테이블은 현재 + 앞뒤 1개만** 유지하고 나머지는 해제(LRU)합니다.

## 7. 전 구간 GPS·센서 — 네 번째 결정

지도에 **전체 경로**를 그리려면 모든 세그먼트의 GPS 패킷이 필요하고,
그건 결국 각 파일의 패킷 헤더를 다 읽어야 합니다 (파일당 ~360ms).

| 방식 | 12파일 | 100파일 |
|---|---|---|
| 즉시 백그라운드 전체 스캔 | ~4초 | ~36초 |
| 재생한 구간만 누적 | 0초 | 0초 |
| 버튼 눌렀을 때만 | 선택 시 위와 동일 | |

**권장**: 폴더를 열면 **백그라운드에서 전체 스캔을 진행률과 함께** 돌리되,
재생은 기다리지 않고 바로 가능하게. 스캔이 끝나면 지도에 전체 경로가 채워집니다.

## 8. 단계별 계획

### 1단계 — 폴더 열기 + 세그먼트 인덱스 · 타임라인

- `webkitdirectory` + 폴더 드래그 앤 드롭
- 헤더 프로브로 즉시 인덱싱 (+ 시각 필드가 비었을 때 폴백)
- 세그먼트 목록: 시각 · 길이 · 크기 · 채널 · 소속 폴더
- **갭·중복 구간 시각화**
- 세그먼트 클릭 → 재생 (기존 단일 파일 경로 재사용)
- 유효하지 않은 파일은 목록에 사유와 함께 표시 (조용히 버리지 않음)

산출물: 폴더를 열면 "언제부터 언제까지, 몇 개 파일, 총 몇 시간, 어디가 비었는지"가 한눈에.

### 2단계 — 연속 병합 재생

- 전역 타임라인 스크럽 (세그먼트 경계 무관)
- 세그먼트 자동 전환 + 미리 읽기
- 빈 구간 건너뛰기
- 패킷 테이블 LRU
- 현재 위치의 **실제 파일명**을 항상 표시 (증거 추적성)

### 3단계 — 다중 소스 · 병합 데이터 · 내보내기

- 겹치는 소스를 트랙으로 분리, 우선순위 규칙 (예: Event > Normal) 또는 수동 선택
- 백그라운드 전체 스캔 → 전 구간 GPS 경로 · 센서 차트
- **구간 지정 내보내기**: 시작~끝을 지정하면 여러 파일에 걸쳐 H.264/WAV/CSV를 이어서 추출
- 폴더 단위 요약 리포트 (파일별 SHA-256 포함)

---

## 9. 증거 취급 관점에서 지킬 것

병합은 **보기 편하게 만드는 것**이지 원본을 바꾸는 게 아닙니다.

- 재생 중 **현재 프레임이 어느 파일의 것인지** 항상 표시
- 내보낸 병합 결과물에는 **구성 파일 목록과 각 SHA-256**을 동봉
- 타임라인의 **빈 구간을 숨기지 않음** (녹화 공백도 사실)
- 겹치는 구간에서 **어느 소스를 썼는지** 명시

## 10. 결정해 주실 것

| # | 질문 | 선택지 |
|---|---|---|
| **D1** | 병합의 의미 | (A) 연속 이어붙이기 / (B) 같은 시각 다중 소스 / (A)+(B) |
| **D2** | 타임라인 축 | 벽시계(갭 유지, 권장) / 연속(갭 제거) / 전환 토글 |
| **D3** | 파일 경계 | 짧은 끊김 허용(권장, 단순) / 무단절 더블 버퍼링 |
| **D4** | 전 구간 GPS | 열자마자 백그라운드 스캔(권장) / 버튼 누를 때만 |

### 함께 알려주시면 좋은 것

- 폴더 구조 (예: `Normal/`, `Event/`, `Parking/` 하위 폴더가 있는지)
- 파일명 규칙 (예: `20260115_090000_NF.jdr` 처럼 시각이 이름에 있는지)
- 파일 하나의 길이 (1분? 3분? 1시간?)와 폴더당 개수
- 전방/후방이 한 파일에 같이 있는지, 파일이 나뉘는지

파일명 규칙을 알면 **헤더 시각 필드가 비어 있어도** 파일명에서 시각을 복원할 수 있어
더 튼튼해집니다.

## 11. 실제 기기 확인 후 바뀐 것

사용자가 실제 SD카드 구조를 확인해 주어, 계획에서 세 가지를 고쳤습니다.

### 실제 구조

```
(SD 루트)
├── config/     3개
├── data/       661개   ← 상시 녹화
├── event/      167개   ← 이벤트 녹화
├── update/     비어 있음
└── viewer.exe  1.86 MB
```

파일은 `00000465.jdr` 같은 **순번 이름**이고 개당 **70MB**, 약 44초 분량입니다.
합계 **828개 · 약 58GB**.

### ① 파일명 시각 폴백은 쓸 수 없다

계획 2장에서 "파일명에 시각이 있으면 폴백으로 쓰겠다"고 했지만, 실제로는 순번뿐입니다.
→ **헤더 시각(+0x94/+0xA4)이 유일한 근거**이고, 헤더가 비면 첫·마지막 패킷에서 읽습니다.
파일명 추출 코드는 다른 기종 대비로 남겨 두되, 순번 이름에서는 동작하지 않음을 테스트로 못박았습니다.

`lastModified`도 믿을 수 없습니다 — `event/` 파일들은 수정 시각이 전부
`2024-09-23 07:13:10`으로 같습니다(미리 할당된 파일로 추정).

### ② 번호 순서 ≠ 시간 순서

루프 녹화는 오래된 파일을 덮어쓰므로 `00000001.jdr`이 `00000465.jdr`보다 **나중**일 수 있습니다.
→ 타임라인은 **반드시 헤더 시각으로 정렬**합니다. 테스트로 고정했습니다.

### ③ 전 구간 GPS 스캔 방식을 바꿨다 (가장 큰 변화)

계획 7장에서는 "파일당 ~360ms"로 잡았는데, 실제 70MB 파일은 전체 파싱에
**2,030ms**가 걸립니다. 828개면 **약 28분** — 쓸 수 없습니다.

해법을 찾았습니다. **12바이트 인덱스 항목에 태그가 들어 있으므로**, 파일을 통째로
파싱하지 않고 인덱스만 읽어 GPS·센서 패킷의 위치를 바로 집어낼 수 있습니다.
그 자리만 골라 읽고, 가까운 항목은 한 번에 묶어 읽습니다.

70MB 파일 1개 실측:

| 작업 | 시간 | 읽은 양 |
|---|---|---|
| 프로브(타임라인용) | **1ms** | 1KB |
| **인덱스 기반 GPS·센서 스캔** | **19ms** | **0.1MB** |
| 재생용 파싱 | 59ms | 70MB |
| ~~전체 파싱 + 해시~~ | ~~2,030ms~~ | ~~140MB~~ |

828개 환산: 타임라인 **0.8초**, 전 구간 GPS 스캔 **약 16초** (28분 → 16초).

### ④ data와 event를 함께 넣으면 겹친다

D1(연속 이어붙이기)에서는 같은 시각 파일이 둘이면 먼저 시작한 쪽을 씁니다.
`event/`는 `data/`와 같은 순간을 담으므로 함께 넣으면 구간이 중복됩니다.

→ **폴더 선택 UI**를 넣었습니다. 기본은 **가장 길게 찍힌 폴더 하나**(보통 `data`)만
선택하고, `event`는 체크로 추가합니다. 겹침이 생기면 요약에 경고를 띄웁니다.

### 남은 확인 사항

- **70MB × 2채널 고화질**을 모바일에서 동시 디코딩할 수 있는지는 실기기 확인이 필요합니다.
  버거우면 한 채널만 재생하는 폴백이 필요합니다.
- 828개 파일을 브라우저가 한 번에 받아들이는지(메모리·핸들 수) 실제 확인이 필요합니다.
